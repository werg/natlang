a typed programming language · spec 0.5-draft · research

Functions whose bodies are paragraphs.

natlang is TypeScript with natural-language functions. The signature is ordinary, checked TypeScript. The body is instructions. A model, possibly a small local one, executes them inside a persistent TypeScript scope, and whatever it hands back has to type-check on the way out.

  • prose: instructions a model executes
  • crisp: types and ordinary code
  • soft: values only a model reads
is_urgent.nl
isUrgent(ticket: string): Promise<boolean>signature fixed
call it on a ticket crisp runs for real · nl answers illustrative

What this page is. An explainer, not a brochure. natlang is a research language and its specification is a 0.5 draft, with a list of known discrepancies in it. Every widget below is a toy re-implementation of one rule from the spec, running in your browser. No model is called. Where a widget shows what a model answered, the answer is illustrative and the widget says so. The running example throughout is the repository's own support-ticket triage.
01
the contract

A signature is a promise you can check.

Γ ⊢ (x₁: τ₁, …) ⇒ τ  decided at compile timebody ∈ Prose
Γ ⊢ nl`body` : (x₁: τ₁, …) ⇒ Promise<τ>
NL-FUN

In most "LLM inside your code" setups a prompt is a string, its answer is a string, and everything in between is hope plus a JSON parser. natlang changes the order of events. The compiler fixes the type of every natural-language call before the model runs, shows that type to the model as part of the call's opening, and checks what comes back after each eval and again at completion.

A wrong-shaped value never reaches your code. It goes back to the model as an error message, and the model repairs it. A call that cannot succeed rejects with a NatlangCallError carrying its outcome, detail and trace, which you catch like any other rejection.

There are two source forms. Inline, a tagged template in TypeScript:

const priority: 'urgent' | 'normal' = await nl`Decide whether ticket is urgent.`(ticket);

Named, a .nl file with YAML frontmatter, imported as an ordinary module. This is the triage example's classify.nl, which the build gives a generated .d.ts:

---
description: Label one ticket using the rubric.
args:
  ticket: string
  rubric: string
returns: Label
---
Pick the label from rubric that fits ticket. If no rule in the rubric covers
the ticket, report an error saying what is missing.

02

    
types before tokens

    
Inference with typed holes.

  


  

    

      

        
Γ, r : ?ρ ⊢ uses(r) ⇝ Cρ = the most specific type satisfying C

        
Γ ⊢ nl`…`(ticket) : Promise<ρ>

      
HOLE


      
You rarely write the type yourself. The compiler collects evidence in a fixed order: an explicit nl<F>, the contextual type of the expression, an immediate call's arguments and result context, and finally later uses of a local.

      
That last step borrows a trick from local type inference in Rust and ML. Each tag whose result is still open gets a fresh placeholder type ?ρ, and the compiler type-checks a second copy of the program. The placeholder flows through ordinary TypeScript: locals, arrays, Promise.all, for…of. Every place it lands adds a requirement.

      
Strong requirements come from what TypeScript expects there (an assignment, an argument, a push) or what the syntax implies (a condition needs boolean, arithmetic needs number, .toUpperCase() names string). Weak ones apply only when nothing strong exists: interpolation into text suggests string, and comparison with a literal suggests its base type. The most specific requirement that satisfies all the others wins. Disagreement is a compile error that cites the statements responsible.

      
Why not infer the type from the model's first answer? Because then the answer would bless itself. The type has to exist before generation so that it can guide generation.See inline natlang lambdas, §Inference rules; implementation in ts-host/src/compiler/holes.ts.

03

    
lexical scope, read aloud

    
Closures, in English.

  


  

    

      

        
x ∈ dom(Γ)x ∈ words(body)x ∉ params

        
x ∈ captures(nl`body`)

      
MENTION


      
An inline nl closes over its lexical scope like an arrow function does. But how does it know which variables it uses when its body is prose? By mention. The compiler tokenizes the instruction text against the names in scope, using case-sensitive JavaScript identifier boundaries. Write policy and you have captured policy. Write "Policy" at the start of a sentence and you have written a word.

      
Explicit parameters shadow captures, as they do in any function. Data captures are read live at each call, not frozen at creation. A mentioned let may be reassigned by the model. The write-back happens after a successful eval and is version-checked: if a sibling call changed the variable in the meantime, the eval fails with capture-conflict and the model retries against the new value. Reassigning a captured const is a compile error. Bindings of function type are always captured by value, which turns out to matter for termination (chapter 5).

      
The occasional false match is an accepted trade-off. The capture list is visible in the child's opening and in the trace.

Data is never instructions: Untrusted<T>

      
The text of a natlang function belongs to its author. A .nl body is fixed text that refers to arguments by name, so a value is never spliced into it. The one splice point is ${…} in an inline template. There the compiler reports untrusted-instruction when the interpolated expression is Untrusted<T>, or text derived from one. The fix it suggests is to pass the value as an argument.

      
Arguments are rendered as data. A marked string shows up as a fenced block whose info line names its source. The fence is three backticks, or one more than the longest run of backticks in the text, so the text can never close its own fence. That last detail is a small one, and a good one.

04

    
what await actually does

    
The model is the interpreter.

  


  

    

      

        
⟨σ, e⟩ ⇓ ok σ′ ⟹ commit σ′⟨σ, e⟩ ⇓ error ⟹ σ unchanged

        
an eval commits all of its changes, or none

      
EVAL

      
When you await a natural-language function, the runtime opens a conversation with a model and offers it a few tools. The central one is eval, which runs TypeScript in a persistent scope. That scope holds the parameters (const and deeply frozen), the captures, the callable items of the function's context, and the host's services. Top-level declarations persist across evals.

      
The model reads, computes, delegates and finishes with return_result(success | blocked | failed). blocked means required information is absent, failed means the instructions asked for something contradictory, and either one comes with a reason sentence instead of a value. Instructions don't all need code: an answer that takes only reading and judgment is given directly.

    

    

      
The details are where it gets good:

      
Cut-offs are honest. A value too long to show is shortened with a note that is deliberately not TypeScript: <<cut off: 37 of 40 items not shown; tickets holds all of it>>. A cut-off literal copied into an eval fails to compile rather than running on part of the data.

      
Errors teach. natlang never spells out a wrong form in a prompt, because that primes the model to produce it. The runtime handles the wrong form and teaches the fix in a one-sentence error.

      
Long conversations compact. Past three quarters of the context budget, the model must call compact_history(note). Older outputs are then replaced by pointers into a searchable transcript.

05

    
no budgets, structurally

    
Termination without a gas meter.

  


  

    

      
Agent frameworks usually stop runaway loops with budgets: max turns, max tokens, a timeout. natlang's house rule is no premature limits. Termination is structural, and it comes from three mechanisms that work together.

      
1. Contexts form a DAG. Every natural-language function is curried over its context, an immutable, content-addressed folder value: (context) => (...args) => Promise<R>. foo.nl can call exactly the items in its companion folder foo/, and each of those items is bound to its own folder. Every call therefore steps down the context graph. Since a context's ID is a hash of its contents, no context can contain itself. Natural-language functions cannot recurse, by construction.

      

        
f ∈ items(ctx)id(ctx) = H(contents(ctx))

        
calls step ctx → ctx(f)  ⟹  the call graph is acyclic

      
DESCEND

    

    

      
review.nl and its callable folderreal FNV hashes

      

        
        

          
          
        

        

      

    

  


  

    
2. Code iterates finitely. Callable-folder TypeScript and eval code may use for…of, counted for loops and array methods. while, do, open for(;;) and generators are rejected. A TypeScript function that is already running in its own call chain may run again only on a smaller argument: a part of its input, a shorter array or string, or a smaller non-negative integer. The same argument must keep getting smaller along the chain. This is the structural recursion of a proof assistant's termination checker, enforced at run time. Have a go:

  

  
will it terminate? · eight small programs0 / 8 answered

  


  

    

      
3. Open-ended work goes through iterateOn. It takes a step function and an initial state, records every step, and returns the first state for which the stopping predicate holds. With a TypeScript predicate you must also give either a measure, a non-negative integer that strictly decreases at every step that continues (a loop variant, as in Hoare logic or Dafny), or a hard step limit. Otherwise the run fails with iteration-unbounded.

      
With a natural-language predicate no bound is required. The predicate runs under a system prompt saying it is a loop's stopping condition, showing the iteration count and whether recent states changed, and asking it to accept a reasonably met criterion rather than demand perfection. A progress judge also reviews the whole trajectory, more often as a run exceeds the per-site step-count statistics (for example, beyond mean+1σ every fourth step, then every second, then every step). A review never stops a run on its own. Only a divergent verdict ends it.

      
// examples/triage/triage.ts, abridged
return await iterateOn(shorten, draft)
  .withLimit({ maxSteps: 3 })
  .until(text => words(text) <= MAX_SUMMARY_WORDS);
// IterationLimitError carries lastState: keep the shortest honest summary.

      
The deliberate exceptions are model-controlled: a loop with a natural-language predicate, and the agent loop of a call, which has no turn or time limit unless the caller sets one.The rules address code written in good faith. The spec says plainly that the Node backend is not a sandbox.

06

    
probabilities and predicates

    
Judgment, typed.

  


  

    

      
Decisions are distributions

      
A function whose result type is finite (a union of literals, boolean, null) may declare readout: decision. The call then offers no tools at all. The runtime asks the model to score every allowed value as the whole reply to the call's opening and returns the most probable one.

      
The normalised distribution is kept in the trace, so a decision is a probability vector. You can grade it with proper scoring rules such as the Brier score, log loss or ranked probability score, and on a Neuralese server you can differentiate it. Host code reads it with runtime.decide(fn, ...args).

      
const d = await runtime.decide(classify, ticket, rubric);
// { value, probabilities: [{ value, probability }],
//   confidence, scored }

      
Drag the bars (or focus them and use the arrow keys) to play the model, then pick the true label to grade it. Notice how log loss punishes confident mistakes far harder than Brier does.

Predicates as types: Is<T, P>

      

        
Γ ⊢ v : Tjudge(v, P) ≥ θ

        
Γ ⊢ v : Is<T, P>

      
REFINE

      
Liquid Haskell refines types with logical predicates. natlang refines them with natural-language ones: type Reply = Is<string, "a reply to the customer that is polite and does not blame them">. Structure is unchanged, so a refined value is a T everywhere. The predicate is an obligation, checked where a value enters a refined slot: a return value, an argument, a declared service result, or an explicit refine(value, predicate). assume skips the check and records the assumption in the trace.

      
The check is a single decision readout. It reads P(true), passes at the threshold, and inside an optional uncertainty band it applies a policy: accept, reject (refinement-undecided), or escalate to a stronger model. A failure on a return goes back to the executing model, which repairs it within a repair budget (3 by default). Verdicts are cached by the SHA-256 of the canonical value, the normalised predicate and the judge, so no value is judged twice.

      
Subtyping falls out cleanly. Is<B, P> fits T whenever B fits T. T fits Is<B, P> too, with the check becoming that site's obligation. Two refinements with the same normalised predicate fit each other without a check.

07

    
call records → compilations

    
A tracing JIT for English.

  


  

    

      

        
guardi(args)∀ j < i. ¬guardj(args)casei active

        
call served by bodyi(args)  ·  otherwise the agent runs

      
CASE

      
The runtime records every call: the definition and its revision, exact inputs and captures, the result, each service call, the eval programs that ran, and the cost. In practice many natural-language functions run the same code for the same kind of input. A tracing JIT notices hot paths, and the specializer does the same for call records. It mines the call store for those patterns and writes a compilation: an ordered list of crisp cases, each one a guard over the arguments and a TypeScript body with the function's signature.

      
The first active case whose guard admits the arguments serves the call, and no model runs. A case that throws or returns the wrong type doesn't fail the call: the agent takes over, told which effects the case already performed. The program's source never changes, and a compilation only applies while the definition's context interface matches the one it was compiled against.

    

    

      
Cases are promoted and demoted by measured comparison with the agent: shadow runs, audits, and a minimum number of comparisons on live calls (three by default). The design notes record why live ones are required. One case passed 496 replays of recorded calls and then failed every live call, because replays share the context the case was written from.

      
Then the nice twist: the specializer is itself a natlang program. worthLooking.nl decides whether a function is worth a look, chooseCondition.nl picks the guard a case should test, and promote.nl decides whether a case moves up, stays or moves down. Crisp code measures each condition exactly.Policy in prose, mechanism in code; see chapter 9.

research extension · 0.5-draft

    
Neuralese: values only models can read.

  


  

    

      

        
v : Neuralese<T>Γ ⊬ v.f, v + 1, if (v)

        
read(v) : Promise<T>  is the only way out

      
OPAQUE

      
When one model hands a result to another, why round-trip through text? Neuralese<T, D> is a soft value of type T: an immutable, ordered block of vectors in dialect D, which a model reads through its read port. It is an abstract type in the classic sense. Host code may store it, pass it and return it, but may not look inside: no field access, no arithmetic, no comparison, no using it as a condition. read is the only route back to a T, and the result is validated like any call result.

      
At the token level a soft value is two control tokens around a run of vectors. Writing is stochastic, gated by a Neuralese temperature τ that is separate from the text temperature. The payload is μ + τ·σ⊙ε, deterministic at τ = 0, which is the inference default. A call that needs Neuralese on a backend without support fails with neuralese-unsupported-backend. There is no text fallback.

Laws, and rewrites in the spirit of GHC

      
natlang:neuralese exports combinators: map, zip, combine, split, read, ask and friends. Each one (except empty and ask) is itself a system natural-language function with a soft body, which makes it trainable. They approximately satisfy algebraic laws: map identity, map fusion, read/map commutation, associativity and identity of combine, split of zip.

      
The compiler uses these laws as rewrite rules to make programs cheaper. Each rule comes with guardrails. A rule matches only syntactic occurrences whose intermediate values have no other use. It never moves a call across an effect. And it is enabled per model and dialect version only after a whole-program comparison on held-out programs shows it does no harm. "≈" is measured through read and downstream consumers, never as equality of vectors.

Fusion you never write down

      
You don't need to write Neuralese anywhere to benefit from it. If natlang check can prove that a stage's result is read only by the next stage, the runtime may keep that hand-off as vectors. The chain is already explicit in the language: a call inside a call (analyze(parse(source))), or a name used exactly once, as the next stage's argument.

      
Any second reader keeps the hand-off as text. That includes an orchestrator peeking at a field, a log line, a second stage, or a different model:. The fix the authoring guide suggests is a sensible one: make the consumer carry forward whatever the orchestrator needed from the middle.

      
Where this is heading: the current research line replaces the vector channel with shared positional KV and hybrid-state spans. Producers export state, and consumers splice it in at the correct positions, with distinct markers for producing and for consuming. It is being trained now. Treat it as a direction, not a result.

09

    
how natlang people build things

    
Policy is prose. Mechanism is crisp.

  


  

    

      
The project's main design rule: before building anything, ask how it would be a natlang program. That means typed natural-language functions, callable folders, services for the outside world, and crisp code only where exactness or the outside world requires it. Any component that decides something (which tier serves, what to fuse, what to promote, how to recover) is a natlang program, and that includes natlang's own runtime and compiler. Crisp code is for services, the CLI, atomic commits, exact verifiers of what the stages produce, and plumbing.

      
When a policy is hot, it gets one interface with both implementations behind a setting. That is the hero widget at the top of this page, and a real primitive:

      
import { pluggable } from '@natlang/node';
const choose = pluggable(
  { crisp: chooseTierCrisp, nl: chooseTier },
  settings.tier,
);
// 'crisp' | 'nl' | 'shadow': shadow runs both, serves one,
// and records a pluggable_shadow event saying whether they agreed.

      
The applications in the repository take this all the way. Most of them ship a DECOMPOSITION.md recording, for every part of the real system, whether it became its own function, one instruction, or a crisp helper, and why.

House rules, from the project's own instructions

  
    
    
  1. Teach in errors, not prompts.Never spell out a wrong form in a prompt, because it primes the model to produce it. Handle it in the runtime and teach the fix in a one-sentence error.
    2. 
    
  2. No premature limits.Termination is structural: no while loops, recursion on a smaller argument, iterateOn with a measure or a predicate. A resource limit gets added when a real problem shows up.
    3. 
    
  3. Measure model-facing changes live.Anything the executing model sees (prompt text, how values render, error wording) is sampled on the live executor, about 48 samples per variant, before it is adopted.
    4. 
    
  4. The interpreter may be small."You are the capable program author; the interpreter may be a small model." Put the algorithm, the decomposition and the data contracts in source, spelled out as numbered steps over named data.
    5. 
    
  5. Stay close to JS.Prefer making standard JavaScript idioms work over inventing new names. Be very circumspect about new model-facing vocabulary.
    6. 
    
  6. One implementation per concept.Before adding a mechanism, find the existing one (specializer, call store, pluggable, refinement shadow) and extend it.
