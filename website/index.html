TypeScript with natural-language functions.

natlang lets you write the parts of a program that need judgment, such as labelling a support ticket or summarizing a report, as typed functions whose bodies are instructions in plain English. A model, often a small local one, carries out the instructions. The compiler fixes each function's types before the model runs, and the runtime checks that what comes back has those types. Everything else is ordinary TypeScript.

The page has nine short chapters. Each ends with an exhibit you can operate: a small JavaScript model of one rule from the specification (version 0.5, a draft). No language model is called.

Model calls are typed function calls. The compiler works out each call's argument and result types before the model runs. A wrong-shaped answer goes back to the model as an error, never to your code. Chapters I and II
Small models are enough. The program holds the algorithm and the data flow. Each natural-language function makes one narrow judgment, which a small local model can carry out. Chapter IX
Programs end by construction. There are no while loops and no recursion between natural-language functions, and open-ended loops need a decreasing measure or an English stopping test. No token budgets are needed. Chapter V
Variables are captured by name. Mention a variable in the instructions and the function reads its current value. Text from outside the program can be marked untrusted, and then it can never become instructions. Chapter III
Every call is recorded. Traces show what the model did. Inputs that always lead to the same code are compiled into plain TypeScript cases that answer without the model. Chapters IV and VII
Judgments are measurable. Finite answers come back as probability distributions, and a type can carry an English predicate that is checked at run time. Chapter VI

I

The contract

IEvery natural-language call has TypeScript types, fixed before the model runs and checked when it returns.

You declare a natural-language function like any other function: typed parameters and one return type. Only the body is different: it is instructions. The compiler settles the signature before any model runs and shows it to the model, and every value the model returns is checked against it.

A wrong value never reaches your code. It goes back to the model as an error, and the model corrects it. Obvious slips, such as "9" where a number is expected, are converted. A call that cannot succeed rejects with a NatlangCallError that carries the outcome, a message and the trace.

Write a function inline, as a tagged template:

const priority: 'urgent' | 'normal' =
  await nl`Decide whether ticket is urgent.`(ticket);

or in its own .nl file, which TypeScript imports like a module:

II
Typed holes

    

    
IIThe compiler infers a call's result type from how the result is used later in the program.

  

  

    

      
You rarely annotate an inline call. The compiler takes its type from an explicit nl<F>, from what the surrounding code expects, or, failing those, from how the result is used later.

      
For that last case it gives the result a placeholder type, ?ρ, checks the program again and collects a requirement from every place the placeholder reaches:

      
    
        
  1. Strong requirements come from what TypeScript expects there (an annotated variable, a parameter, a typed array) or what the syntax needs: a condition needs boolean, arithmetic needs number.
    2. 
        
  2. Weak requirements count only when nothing is strong: printing the value suggests string, and comparing it with a literal suggests that literal's type.
    3. 
        
  3. The type is the most specific requirement that fits all the others. If none fits, compilation fails with nl-ambiguous-signature and points at the conflicting lines.
    4. 
      

      
This is the idea behind Hindley–Milner type inference, applied to calls whose bodies are prose. The model's answer never decides the type; the type has to exist first so that it can guide the answer.

      

        
Γ, r : ?ρ ⊢ uses(r) ⇝ Cρ = the most specific type satisfying C

        
Γ ⊢ nl`…`(ticket) : Promise<ρ>

III
Closures in English

    

    
IIIAn inline natural-language function captures the variables its instructions mention by name.

  

  

    

      
An inline nl function can use the variables around it, like an arrow function. It uses exactly the ones its instructions name: the compiler matches the words of the instruction against the variables in scope, case-sensitively. "Judge note against policy" captures note and policy; "Policy says…" captures nothing.

      
Captured values are read when the function is called, not when it is created. The model may assign to a captured let; the new value is written back after a successful step, and if another call changed the variable first, the step is retried. Assigning to a captured const is a compile error.

      
Each call's trace lists what it captured, so an English word that happens to match a variable name is easy to spot.

      

        
x ∈ dom(Γ)x ∈ words(body)x ∉ params

        
x ∈ captures(nl`body`)

Text from outside the program, such as an email, can be typed Untrusted<T>. It always reaches the model as data. Interpolating it into instructions with ${…} is a compile error, untrusted-instruction, and the fix is to pass it as an argument.

      
The model sees untrusted text in a fenced block labelled with its source. The fence is longer than any run of backticks in the text, so the text cannot close the block and pose as instructions.

IV
The interpreter

    

    
IVWhen you await a natural-language function, a model works in a TypeScript scope until it returns a typed result.

  

  

    

      
The model works in steps. Its main tool, eval, runs TypeScript in a scope that holds the call's arguments, the captured variables, the functions it may call and the host's services. Variables declared in one step are still there in the next.

      
It finishes with return_result: success with a value of the declared type, blocked when information is missing, or failed when the instructions contradict themselves, the last two with a one-sentence reason. A question that needs only reading is answered directly.

      
A failed step changes nothing in the scope, although effects it already performed, such as service calls, remain. Long values are shown cut off, with a note naming the variable that holds all of it. When a conversation grows long, the model summarizes it and the full history stays searchable.

    

    

      

        
⟨σ, e⟩ ⇓ ok σ′ ⟹ commit σ′⟨σ, e⟩ ⇓ error ⟹ keep σ

V
Termination

    

    
Vnatlang programs end because of how they are structured, not because of turn, token or time budgets.

  

  

    

      
natlang has no turn, token or time budgets. Programs end because three rules leave no way to loop forever.

      
1. Natural-language functions cannot call themselves. foo.nl may call only the items in its folder foo/, and each folder is identified by a hash of its contents. Calls therefore always move down a tree of folders and can never return to a caller.

      

        
f ∈ items(ctx)id(ctx) = H(contents(ctx))

        
calls go from ctx to ctx(f), so the call graph is acyclic

3. Open-ended work uses iterateOn(step, initial), which repeats a step until a stopping test passes. A TypeScript test needs a step limit or a number that shrinks every step; without one the loop is refused with iteration-unbounded. An English test needs neither, but a progress judge reviews long runs and can end one that has stopped making progress.

      
The model's own loop within a single call has no limit unless the caller sets one. These rules prevent accidental infinite loops; they are not a sandbox. The triage example caps its summary loop at three steps:

      
return await iterateOn(shorten, draft)
  .withLimit({ maxSteps: 3 })
  .until(text => words(text) <= MAX_SUMMARY_WORDS);

VI
Judgment, typed

    

    
VIA call with a finite result type can return a probability distribution, and a type can carry a natural-language predicate.

  

  

    

      
When a function returns one of a few values, such as a label, it can declare readout: decision. The model then scores every allowed value instead of writing an answer, and the call returns the most likely value together with the whole distribution:

      
const d = await runtime.decide(classify, ticket, rubric);
// { value, probabilities: [{ value, probability }],
//   confidence, scored }

      
A distribution can be graded with proper scoring rules. In the exhibit, set the probabilities, pick the true label and compare the scores: log loss punishes a confident mistake far more than the Brier score does.

A type can also carry a condition written in English: Is<string, "a reply to the customer that is polite and does not blame them">. The value is still a string. The condition is checked when the value is returned, passed as an argument or wrapped with refine(); assume() skips the check and records that it did.

      
The check asks a model for the probability that the condition holds and compares it with a threshold. Close calls can be accepted, rejected or sent to a stronger model. A failed return goes back to the executing model to fix, up to three times by default, and each verdict is cached.

      

        
Γ ⊢ v : Tjudge(v, P) ≥ θ

        
Γ ⊢ v : Is<T, P>

VII
A JIT for English

    

    
VIIRecorded calls are compiled into guarded TypeScript cases that answer some calls without a model.

  

  

    

      
Every call is recorded: its inputs, the code the model ran, service calls, the result and the cost. Many functions run the same code for the same kind of input. The specializer finds those patterns and writes cases, each a condition on the arguments plus the TypeScript that produces the answer.

      
When a case's condition matches, the case answers instead of the model. If it fails, the model takes over and is told what the case already did. Your source code never changes.

      
Cases have to earn their place. They run in shadow beside the model before promotion and are audited afterwards, and at least three comparisons must be on live calls: one case passed 496 replays of old calls and then failed every live one. The specializer is itself written in natlang.

    

    

      

        
guardi(args)no earlier guardj(args)casei active

        
bodyi(args) answers; otherwise the model runs

VIII
Neuralese

    

    
VIIIA research extension: typed values kept as a model's internal state, which only a model can read.

  

  

    

      
When one model call's output goes straight into another call, turning it into text and reading it again throws away the work the model did. Neuralese<T> is a value of type T kept as the model's own state. The producing call writes it between <|neuralese_produce|> markers, and the runtime keeps the attention keys and values for that span, plus the convolution and recurrent state on hybrid models such as LFM. A consuming call splices that state in, at its original positions, between <|neuralese_consume|> markers.

      
Your code can store and pass such a value but cannot look inside; read() turns it back into a checked T. The value also keeps its text and the tokenizer it came from. Its state is reused only by the same checkpoint, tokenizer and architecture. Any other reader gets the text, tokenized again with its own tokenizer, which is a best effort; a model of another architecture must declare that it accepts this, or use a learned adapter. Using Neuralese on a backend that does not support it is an error; there is no silent fallback to text.

      

        
v : Neuralese<T>v.f, v + 1, if (v): rejected

        
read(v) : Promise<T>

The operations on these values (map, zip, combine, split, read, ask) are themselves trainable natural-language functions. They roughly obey algebraic laws, such as map fusion: map(map(v, g), f) ≈ map(v, compose(f, g)).

      
The compiler uses these laws to remove model calls, like GHC's rewrite rules. A rule fires only where the intermediate value is used once, never across a side effect, and only after a test on held-out programs shows it does no harm. IX
Policy & mechanism

    

    
IXDecisions are written as natural-language functions; exact work stays in TypeScript.

  

  

    

      
natlang projects follow one rule: write decisions as natural-language functions and keep exact work in TypeScript. Choosing a model, deciding what to merge or how to recover from an error are decisions. Services, storage and checking what the decisions produced are exact work. natlang's own runtime is built this way too.

      
When a decision is performance-sensitive, it gets both versions behind one switch. The isUrgent example at the top of the page uses this:

      
import { pluggable } from '@natlang/node';
const choose = pluggable(
  { crisp: chooseTierCrisp, nl: chooseTier },
  settings.tier,
);
// 'crisp' | 'nl' | 'shadow': shadow runs both, serves one,
// and records whether they agreed.

    

    

      
Rules the project follows when writing for models:

      
    
        
  • Never show a wrong form in a prompt, because it primes the model to produce it. Handle it in the runtime and explain the fix in a one-line error.
    • 
        
  • Add a resource limit only after a real problem; termination comes from structure (chapter V).
    • 
        
  • Test any change the model sees, such as a prompt or an error message, on the live model, about 48 samples per variant, before adopting it.
    • 
        
  • Assume the model is small: put the algorithm and the data contracts in the source, as numbered steps.
    • 
        
  • Make ordinary JavaScript idioms work rather than inventing new names.
    •
