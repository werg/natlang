Functions whose bodies are paragraphs.

natlang is TypeScript with natural-language functions. A natural-language function has an ordinary, checked TypeScript signature, and its body is instructions. A model, possibly a small local one, executes the instructions inside a persistent TypeScript scope, and the value it returns must match the signature.

Start with plate I Read the specification

Each exhibit on this page is a small JavaScript model of one rule from the specification and runs in your browser. No language model is called; where an exhibit shows a model's answer, the answer is an example and is marked as one. The specification is a draft, version 0.5.

I

The contract

IThe compiler fixes the type of every natural-language call before the model runs, and the runtime checks what comes back.

A natural-language function has an ordinary TypeScript signature: typed parameters and one return type. Its body is instructions. The compiler works out the signature before any model runs and shows it to the model as part of the call. The runtime checks each value the model hands back, after every eval and again when the call finishes.

A value of the wrong shape does not reach your code. It goes back to the model as an error message, and the model corrects it. Simple scalar mistakes, such as a number written as a string, are converted when the intended type is unambiguous. A call that cannot succeed rejects with a NatlangCallError carrying its outcome, a detail message and the trace.

Functions come in two forms. Inline, as a tagged template in TypeScript:

const priority: 'urgent' | 'normal' =
  await nl`Decide whether ticket is urgent.`(ticket);

Or named, as a .nl file with YAML frontmatter, which TypeScript imports like a module. This is classify.nl from the triage example:

---
description: Label one ticket using the rubric.
args:
  ticket: string
  rubric: string
returns: Label
---
Pick the label from rubric that fits ticket. If no rule in the rubric covers
the ticket, report an error saying what is missing.

II
Typed holes

    

    
IIThe compiler infers a call's result type from how the result is used later in the program.

  

  

    

      
Most inline calls carry no type annotation. The compiler finds the type before the model runs, from four sources in order: an explicit nl<F>, the type the surrounding expression expects, the arguments and result of an immediate call, and finally the later uses of a local variable.

      
For the last source the compiler gives the call a placeholder result type, ?ρ, and type-checks the program a second time. The placeholder flows through ordinary TypeScript (variables, arrays, Promise.all, for…of), and every place it reaches adds a requirement.

      
    
        
  1. Strong requirements come from what TypeScript expects at that point, such as an annotated assignment, a function argument or a push into a typed array, or from what the syntax implies: a condition needs boolean, arithmetic needs number, and .toUpperCase() needs string.
    2. 
        
  2. Weak requirements count only when there is no strong one. Interpolating the value into text suggests string; comparing it with a literal suggests that literal's base type.
    3. 
        
  3. The result type is the most specific requirement that satisfies all the others. If none does, compilation fails with nl-ambiguous-signature, and the message cites the conflicting lines.
    4. 
      

      
This works like Hindley–Milner inference, where an unknown type is a variable solved from how a value is used. The model's first answer is never used to decide the type, because the type has to exist before generation in order to guide it.

      

        
Γ, r : ?ρ ⊢ uses(r) ⇝ Cρ = the most specific type satisfying C

        
Γ ⊢ nl`…`(ticket) : Promise<ρ>

III
Closures in English

    

    
IIIAn inline natural-language function captures the variables its instructions mention by name.

  

  

    

      
An inline nl function closes over the variables in scope, as an arrow function does. Because its body is prose, the compiler decides which variables it uses by matching the words of the instruction against the names in scope, using case-sensitive JavaScript identifier boundaries. The word policy captures the variable policy; the word "Policy" at the start of a sentence does not.

      
Explicit parameters take precedence over captures. Captured data is read at each call, not when the function is created. If the instruction mentions a let variable, the model may assign to it. The new value is written back after a successful eval; if another call changed the variable in the meantime, the eval fails with capture-conflict and the model retries. Assigning to a captured const is a compile error. Variables of function type are captured by value, which chapter V relies on.

      
An ordinary English word that happens to match a variable name is captured too. The capture list appears in the call's opening and in its trace, so this is visible.

      

        
x ∈ dom(Γ)x ∈ words(body)x ∉ params

        
x ∈ captures(nl`body`)

Text from outside the program, such as an email or an HTTP body, can be typed Untrusted<T>. A .nl body is fixed text, so the only place a value could become part of the instructions is a ${…} interpolation in an inline template. The compiler rejects interpolating an untrusted value there with untrusted-instruction and suggests passing it as an argument instead.

      
Arguments are shown to the model as data. Untrusted text appears in a fenced block labelled with its source. The fence is three backticks, or one more than the longest run of backticks in the text, so the text cannot end the fence early.

IV
The interpreter

    

    
IVWhen a natural-language function is awaited, a model runs TypeScript in a persistent scope until it returns a result.

  

  

    

      
A call opens a conversation with a model and offers it a few tools. The main one is eval, which runs TypeScript in a persistent scope. The scope holds the parameters (constant and deeply frozen), the captured variables, the functions in the call's context and the services the host provides. Declarations made in one eval are available in the next.

      
The model finishes with return_result and one of three statuses: success with a value of the declared type, blocked when required information is missing, or failed when the instructions ask for something contradictory. The last two carry a one-sentence reason instead of a value. A task that needs only reading and judgment can be answered directly, without running code.

      
An eval is atomic: if it fails, none of its changes to variables are kept, although effects such as service calls remain. Values too long to show are cut off with a note naming the variable that holds all of it, for example <<cut off: 37 of 40 items not shown; tickets holds all of it>>; a cut-off value pasted into code fails to compile rather than running on partial data. Errors explain the fix in one sentence. When the conversation reaches three quarters of its context budget, the model must summarize its progress with compact_history, and older outputs remain searchable through transcript.

    

    

      

        
⟨σ, e⟩ ⇓ ok σ′ ⟹ commit σ′⟨σ, e⟩ ⇓ error ⟹ keep σ

        
an eval commits all of its changes or none

V
Termination

    

    
Vnatlang programs end because of how they are structured, not because of turn, token or time budgets.

  

  

    

      
natlang does not stop runaway programs with budgets. Three rules make programs end on their own.

      
First, contexts form a directed acyclic graph. Each natural-language function is bound to its context: an immutable folder of functions and data whose ID is a hash of its contents. foo.nl can call only the items in its folder foo/, and each of those is bound to its own folder, so every call moves down the graph. A folder cannot contain its own hash, so natural-language functions cannot call themselves, directly or indirectly.

      

        
f ∈ items(ctx)id(ctx) = H(contents(ctx))

        
calls go from ctx to ctx(f), so the call graph is acyclic

Second, code in callable folders and in eval uses only finite loops: for…of over a fixed collection, counted for loops and array methods. while, do, open for(;;) and generators are rejected. A TypeScript function may call itself only on a smaller argument (part of its input, a shorter array or string, or a smaller non-negative integer). This is the rule a proof assistant's termination checker enforces, checked here at run time. Decide what happens to each program below.

  

  
0 / 8 answered

  


  

    

      
Third, open-ended work goes through iterateOn(step, initial), which records every step and returns the first state that satisfies a stopping predicate. A TypeScript predicate requires either a measure, a non-negative integer that must decrease at every step that continues (a loop variant), or a step limit. Without one the run fails with iteration-unbounded.

      
A natural-language predicate needs neither. It is told that it is a loop's stopping condition and asked to accept a reasonably met criterion. A progress judge reviews the whole trajectory, more often as the run grows longer than usual for that call site. Only a divergent verdict from the judge ends the run.

      
Two loops are left to the model on purpose: an iterateOn with a natural-language predicate, and the agent loop of a single call, which has no turn limit unless the caller sets one. The rules prevent accidental infinite loops; the specification states that the Node backend is not a sandbox. The triage example uses a step limit:

      
return await iterateOn(shorten, draft)
  .withLimit({ maxSteps: 3 })
  .until(text => words(text) <= MAX_SUMMARY_WORDS);

VI
Judgment, typed

    

    
VIA call with a finite result type can return a probability distribution, and a type can carry a natural-language predicate.

  

  

    

      
A function whose result type is finite (a union of literals, boolean or null) may declare readout: decision. The call then offers the model no tools. The runtime asks the model to score every allowed value as the reply to the call's opening and returns the most probable one.

      
The normalized scores are kept in the trace, so each decision is a probability vector. It can be graded with proper scoring rules such as the Brier score, log loss or the ranked probability score, and on a Neuralese server it can be differentiated. Host code reads it with runtime.decide:

      
const d = await runtime.decide(classify, ticket, rubric);
// { value, probabilities: [{ value, probability }],
//   confidence, scored }

      
In the exhibit, drag the bars (or focus them and use the arrow keys) to set the probabilities, then choose the true label. Log loss penalizes a confident wrong answer much more than the Brier score does.

A type can also carry a predicate written in English: Is<string, "a reply to the customer that is polite and does not blame them">. The value is still a string everywhere. The predicate is checked when a value enters a refined position: a return value, an argument, a declared service result, or an explicit refine(value, predicate). assume skips the check and records the assumption in the trace.

      
The check is a single decision readout that estimates the probability the predicate holds. A value passes at or above the threshold. Inside an optional uncertainty band a policy applies: accept, reject with refinement-undecided, or escalate to a stronger model. A failed return goes back to the model, which may repair it up to three times by default. Verdicts are cached by the SHA-256 of the value, the normalized predicate and the judge.

      
The subtyping rules are simple. Is<B, P> can be used wherever B can. A plain T can be used where Is<B, P> is expected, and the check happens there. Two refinements with the same normalized predicate are interchangeable without a check.

      

        
Γ ⊢ v : Tjudge(v, P) ≥ θ

        
Γ ⊢ v : Is<T, P>

VII
A JIT for English

    

    
VIIRecorded calls are compiled into guarded TypeScript cases that answer some calls without a model.

  

  

    

      
The runtime records every call: the definition and its revision, the exact inputs and captures, the result, each service call, the code the model ran and the cost. Many natural-language functions run the same code whenever they see the same kind of input. The specializer looks for those patterns in the call store, as a tracing JIT looks for hot paths, and writes a compilation: an ordered list of cases, each a guard over the arguments and a TypeScript body with the function's signature.

      
The first active case whose guard accepts the arguments serves the call, and no model runs. If a case throws or returns a value of the wrong type, the call does not fail; the model handles it and is told which effects the case already performed. The program's source never changes, and a compilation applies only while the function's context matches the one it was compiled against.

      
Cases are promoted and demoted by comparing them with the model: shadow runs, audits of served calls, and a minimum number of comparisons on live calls (three by default). The live comparisons were added after one case passed 496 replays of recorded calls and then failed every live call, because the replays shared the context the case had been written from. The specializer itself is a natlang program: worthLooking.nl, chooseCondition.nl and promote.nl make its decisions, and TypeScript measures each condition exactly.

VIII
Neuralese

    

    
VIIIA research extension: typed values made of vectors, which only a model can read.

  

  

    

      
When one model's result goes straight to another model, it need not be converted to text. Neuralese<T, D> is a soft value of type T: an immutable sequence of vectors in dialect D, which a model reads directly. It is an abstract type. Host code may store, pass and return a soft value but may not look inside it: no field access, arithmetic, comparison or use as a condition. read is the only way back to a T, and its result is validated like any call result.

      
To a model, a soft value is a run of vectors between two control tokens. Writing one is stochastic, controlled by a Neuralese temperature τ separate from the text temperature: the payload is μ + τ·σ⊙ε, which is deterministic at the default τ = 0. A call that needs Neuralese on a backend without support fails with neuralese-unsupported-backend; there is no text fallback.

      

        
v : Neuralese<T>v.f, v + 1, if (v): rejected

        
read(v) : Promise<T>

The module natlang:neuralese provides combinators: map, zip, combine, split, read, ask and others. Except for empty and ask, each is itself a natural-language function with a soft body, so it can be trained. They approximately satisfy algebraic laws: map identity, map fusion, read/map commutation, associativity and identity of combine, and split of zip.

      
The compiler uses these laws as rewrite rules to make programs cheaper, in the manner of GHC's rewrite rules. A rule applies only where the intermediate value has no other use, never moves a call across an effect, and is enabled for a model and dialect version only after a comparison on held-out programs shows that it does no harm. Approximate equality is measured through read and the downstream results, not by comparing vectors. Click a highlighted expression to apply a rule.

A program can benefit from Neuralese without mentioning it. When natlang check can prove that a stage's result is read only by the next stage, the runtime may keep that hand-off as vectors. The language already expresses this: a call inside a call, as in analyze(parse(source)), or a name used exactly once, as the next stage's argument.

      
Any second reader keeps the hand-off as text: the orchestrator reading a field, a log line, a second consumer, or a different model: setting. The authoring guide recommends having the consumer pass along whatever the orchestrator needs from the middle value.

      
Current research replaces the vector channel with shared positional key-value and hybrid-state spans: producers export model state, and consumers import it at the correct positions, with separate markers for producing and consuming. This work is being trained now and has no results to report yet.

IX
Policy & mechanism

    

    
IXDecisions are written as natural-language functions; exact work stays in TypeScript.

  

  

    

      
The project's design rule is to start every component as a natlang program: typed natural-language functions, callable folders, and services for the outside world, with ordinary code only where exactness or the outside world requires it. Any component that makes a decision, such as which model serves a call, what to fuse, what to promote or how to recover, is a natlang program, including parts of natlang's own runtime and compiler. TypeScript handles services, the command line, atomic commits, exact checks of what the natural-language stages produce, and plumbing.

      
When a decision is on a hot path, it gets one interface with both implementations behind a setting. Exhibit A on the home section uses this primitive:

      
import { pluggable } from '@natlang/node';
const choose = pluggable(
  { crisp: chooseTierCrisp, nl: chooseTier },
  settings.tier,
);
// 'crisp' | 'nl' | 'shadow': shadow runs both, serves one,
// and records a pluggable_shadow event saying whether they agreed.

    

    

      
The project's working rules for model-facing design:

      
    
        
  • Wrong forms are never spelled out in a prompt, because that primes the model to produce them. The runtime handles them and explains the fix in a one-sentence error.
    • 
        
  • No resource limits are added before a problem appears. Termination comes from structure, as described in chapter V.
    • 
        
  • Any change the executing model sees, including prompt text, value rendering and error wording, is sampled on the live model, about 48 times per variant, before it is adopted.
    • 
        
  • The program author is expected to be capable and the interpreter may be a small model, so the algorithm, decomposition and data contracts go in the source, written as numbered steps over named data.
    • 
        
  • Standard JavaScript idioms are made to work in preference to inventing new names.
    •
