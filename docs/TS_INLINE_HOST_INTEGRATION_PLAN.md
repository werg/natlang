# TypeScript-native natlang integration: implementation plan

## Target contract

A TypeScript project can use natural-language functions at any expression site:

```ts
import { nl, createNatlangRuntime } from '@natlang/node';

const runtime = createNatlangRuntime({ model: teacher, trace: traceSink });

await runtime.run(async () => {
  let policy = loadPolicy();
  const verdict: Verdict = await nl`
    Read evidence against policy. Return a Verdict and explain uncertainty.
  `(evidence);
  await saveVerdict(verdict);
});
```

The `nl` expression is a real asynchronous callable. Its explicit inputs come from the call; exact mentions of visible lexical names capture live bindings. The compiler obtains its input and return target from TypeScript context **before** the model runs. The existing lambda interpreter still owns line discharge, typed return validation, traces, errors, and child execution. `nl` uses stock TypeScript syntax and needs a natlang-aware compile/check step, as specified in [Inline natural-language lambdas](inline-natlang-lambdas.md).

`runtime.run` in this sketch establishes a context for an ordinary TypeScript task. It is **not** a second way to run a natlang program or an instruction to put one root lambda around an app. An application can call compiled `nl` functions anywhere in that task, including in a handler, library, callback, test, or another natlang lambda. A project-level runtime can create many independent tasks and dispose of its owned resources. The browser API has the same shape and semantics; its model configuration and context-propagation mechanism differ (see below).

**Keep scoped callable items.** A named `foo.nl` lambda has a callable namespace made only from items in its sibling `foo/` directory. It cannot directly call a natlang function elsewhere in the project, even when host TypeScript could import that function. This is an authority rule enforced by the compiler/linker and runtime, not only a prompt convention. An anonymous `nl` created during `foo.nl` execution sees **the same callable context** as `foo.nl`, including its children; it is not given an empty or narrower list. A callable TypeScript file inside `foo/` may import sibling `.ts` and `.nl` functions, call those imported functions, and define or call anonymous `nl` lambdas in its own code. Those anonymous lambdas inherit the same `foo/` callable context. Ordinary TypeScript dependencies still work; these imports do not add outside natlang callables to the interpreting agent's namespace. The compiler checks natlang callable references through aliases and captures so they cannot widen that namespace. Host-authored TypeScript outside a natlang invocation can import named lambdas from elsewhere in the project and call them, subject to its application authority. Keep `.nl` as the named, scoped, agent-editable lambda source form; the new inline form complements it rather than erasing it.

**Application callable context: `natlang.d/`.** An inline `nl` in ordinary application code (outside any callable folder) gets the callable context of the nearest ancestor directory that contains a `natlang.d/` folder. `natlang.d/` follows exactly the rules of a `foo/` companion folder: its `.nl` and `.ts` items, with their own companion folders, form the callable tree shown under **imports**; the constrained-TypeScript policy applies inside it; and host TS may import its items directly. A package normally has one `natlang.d/` at its root; a subdirectory may add its own to give code below it a different context (nearest wins, no merging). An inline `nl` with no `natlang.d/` above it has an empty callable context and works only with its explicit inputs and captures. A captured function value remains callable through its live handle; capturing is how host code grants an extra function to one child.

**Disallow recursion across the scoped authoring surface.** Reject direct and mutual recursion among named `.nl` lambdas, inline `nl` lambdas, and authored TypeScript functions in their callable folders (including `natlang.d/`). Include cycles routed through sibling imports, record properties, callbacks, captured callables, and `folder.apply`. Statically diagnose cycles when the compiler can resolve them; instrument callable entries so a runtime guard rejects reentry through a dynamic route before its body runs. Recursion means a definition appearing in **its own chain of callers**: each invocation carries its ancestor definition IDs, and entry fails if its own ID is among them. Concurrent calls of one definition from the same parent, such as `Promise.all(notes.map(note => judge(note)))`, are siblings rather than reentry and are allowed, as are repeated sequential calls. No depth limit is presented as a substitute for this rule.

**Represent the injected callable context as a hierarchy.** JavaScript functions can have properties, so the functions already injected into the interpreting agent's `eval` scope can be callable objects with typed child attributes. For example, if `summarize.nl` has `summarize/is_short.ts` and `summarize/shorten.nl`, the injected `summarize` value supports both `await summarize(text)` and `summarize.is_short(text)` / `await summarize.shorten(text)`. A deeper `summarize/shorten/revise.nl` appears as `summarize.shorten.revise`. Show this same tree, with rendered signatures and source kinds, under **imports** in the agent's scope opening; the agent should not need to infer it from a flat list or perform another import. A `foo.nl` invocation receives the subtree rooted in `foo/` as its callable context, and its anonymous descendants receive that same subtree. The current lambda is not reintroduced as its own callable root.

The root of a codebase listing shows its top-level items directly: `summarize.nl` is `summarize`, not `codebase.summarize`. A TypeScript module no longer needs a default-exported function. If `textTools.ts` has named exports `normalize` and `score`, the injected value is `textTools.normalize` and `textTools.score`; if it exports a record, retain that record's typed nesting, such as `textTools.rules.strict`. A default function export, when present, makes the module value itself callable, and its named exports can be attributes of that callable. A default record export makes the module value a record. Present the same module/export/property paths in the imports listing and in `read_function`/`edit_function` addresses, with each path resolving to the source file that defines it. When `textTools.ts` and a `textTools/` folder coexist, they form one node: the module's exports and the folder's children are merged as attributes, and a name defined by both is a source diagnostic. Code in `textTools.ts` may import items from `textTools/`, just as `foo.nl` calls items in `foo/`. Show runtime values that are safe to inspect as typed values; type-only exports appear in the type listing, never as phantom runtime imports. This lets an agent reading `textTools.ts` see the same structure it uses in `eval`. Crisp modules are evaluated as module instances (one per source revision) rather than as a single default function body per call, so module-level state lives for a revision and resets when an edit publishes a new one.

```text
imports
  summarize(text: string): Promise<Summary>        # summarize.nl
    .is_short(text: string): boolean                # summarize/is_short.ts
    .shorten(text: string): Promise<string>         # summarize/shorten.nl
  textTools                                        # textTools.ts
    .normalize(text: string): string               # named export
    .rules.strict: Rule                            # record export
```

The compiler produces typed callable objects or module records and a matching tree of definition IDs; property access resolves through that tree and the current scope authority. Child properties are read-only as bindings but point to live definitions, so an allowed codebase content edit affects later calls. This is a display and value-shape change to the existing injected functions, not a new TS module import mechanism. Diagnose properties on callable nodes that collide with intrinsic/inherited function properties (`call`, `apply`, `bind`, `name`, `length`, `prototype`, `constructor`, `__proto__`, etc.), `then` (which would accidentally make the function a thenable), or the standard natlang `iterateOn` method. Use a source diagnostic rather than an implicit alias. Define permitted child properties with `Object.defineProperty`, never prototype-sensitive assignment. Recursion checks follow property calls just as they follow direct calls.

For a directory reducer, keep the same callable and interpreter. Its extra authority is an explicit `Folder` argument and the `commit` tool. A folder-authorized caller can use `const value = await folder.apply(reducer, ...inputs)` to obtain the typed return while the folder handle receives the committed change, or `const value = await reducer(folder, ...inputs)` when it wants the typed return only. An ordinary lambda without folder authority cannot call a directory reducer. `return` and `commit` have the same completion point; `commit` also extracts the patch. Folder writes serialize at the folder authority boundary. The ordinary codebase remains readable and content-editable through its separate codebase tools; it cannot add, move, or delete codebase files. This distinction is in the invocation's authority, not a second execution engine.

There is a second, unrelated use of **reducer** in the current terminal/browser application wrappers: a source path that maps `(state, event)` to new state, followed by a separate source path for a view. This is application orchestration, not the directory-reducer lambda subtype. Keep its useful behavior—serial event dispatch, duplicate event IDs, durable commit before publish, cancellation, trace/run IDs, and retrying a failed view without replaying a committed event—but implement it as ordinary TS application code or a small optional callback-based utility. Its `reduce` and `view` callbacks may call named or inline natlang functions wherever needed. They are not mandatory program roots or a distinct natlang host mode.

## What to retire

| Current integration | Decision | Replacement |
|---|---|---|
| Node `NativeNatlangHost.run({ source, inputs, modelTurn })` and browser `BrowserNatlangHost.run(...)` as the normal application API | Retire after migration | A configured runtime context and direct calls of compiled TypeScript `nl` functions |
| Separate `program`, `definitions`, `files`, and path-root request variants | Retire from the public app API | TypeScript modules and typed calls; fixtures and IR can enter the private invocation kernel |
| `BrowserNatlangClient` as an app-facing run-by-file transport | Retire | Browser runtime binding plus a model transport; worker messaging remains an implementation detail |
| Terminal and browser reducer/view root frameworks | Retire as natlang-specific integration styles | Ordinary TypeScript state/event/view code calling `nl` wherever semantic work belongs |
| `.nl` path loading as a **root application entry**, plus mandatory default-export `.ts` app source trees | Retire as entry formats | Ordinary TypeScript app entry modules calling inline or imported named lambdas |
| `foo.nl` plus sibling `foo/` callable items | Keep and strengthen | Named, agent-editable lambdas with a compiler/runtime-enforced child callable namespace |
| Map, Fold, and Iterate nodes; `call` with `over`/`until`/`init`/`max`; `Map<>`/`Fold<>`/`Iterate<>`/`LoopVerdict` in the type grammar; root stream requests | Retire | Ordinary TS: `Promise.all` over a callable for parallel maps, a `for ... of` loop for folds, async iterables in host code for streams, and `iterateOn` for open-ended iteration. Model-backend concurrency limits replace `mapWorkers` |
| `fx.<capability>.<op>` effects, `effects:` frontmatter, per-run `capabilities`, and the untyped `host` global | Retire | Typed host services (see **Effects and host services**) |
| Python applications on the legacy Python runtime (`applications/*.py`) | Retire with the Python runtime | Port apps still worth keeping to TS entry modules; Python training and IR scripts stay Python and read the new IR |
| `.nlpkg` archives and CLI launches | Retain only as distribution and process adapters | Package and launch compiled TypeScript entry modules; no reducer/view names or alternate program execution protocol in the manifest |
| Node and browser runtime cores | Keep **one shared invocation kernel** | Platform adapters supply model, filesystem, module loading, and capabilities |

The remaining entry-path audit is part of the migration, not an exception list:

| Entry path today | Current role | Target |
|---|---|---|
| `NativeSourceWorkspace.invoke` | Explicit child runs from host TS, with its own `NativeRuntime.runRoot` | Typed imported callable using the current task context; preserve source revision, trace, and parent call ID |
| Browser playground `runPlaygroundProject` | Validates a virtual file tree, then calls `host.run({kind: 'files'})` | Compile a virtual TS project and invoke its exported function through the same kernel; keep trace navigation as a viewer |
| CLI direct `.nl`/`.ts`/YAML/JSON source execution | Starts a root run from a file or program document | Launch a TS entry module; keep a developer runner for a named `.nl` function as a thin generated TS caller if useful, not a second execution protocol |
| Package target `createTarget` | Trusted adapter with reducer/view manifest paths | Keep trusted process adapter, model setup, package pinning, and authority declaration; call compiled TS entry code without reducer/view fields |
| Teacher collector, source workspace, conformance, and research scripts | Call `runRoot` or `host.run` on generated fixtures | Compile and invoke through the same kernel with injectable model driver and trace sink; retain fixture/IR serialization outside the public app API |
| Studio child workers and browser-local demo | Carry file-root requests to browser host/client | Keep worker/model lifecycle as transport; invoke compiled TS tasks and route live handles to their owner realm |
| Root `Fold` stream request | Special `over` stream on a root program | Removed with the other bespoke loop primitives; use ordinary async iterables in TS, calling natlang functions within the loop |

This audit leaves several adapters and utilities, but only **one way to invoke natlang functions**. Model loading, packaging, event state, DOM rendering, CLI launch, and trace viewing are useful services; none needs to decide what a natlang function is or duplicate its execution lifecycle.

The archive can still pin dependencies and declare authority. The CLI can still launch an app. Neither should define a second language surface. During implementation, old paths may exist on a branch so migration can be checked; the release cutover removes them rather than leaving permanent compatibility branches. Do not keep a generic YAML or `Pending` root request in the supported SDK just to preserve old examples. Internal research fixtures may call the kernel directly.

This simplification also removes the current global `running` guards on Node/browser hosts as an application concurrency policy. Independent TypeScript tasks should run concurrently. Only folder writes serialize; captured cells use version-checked write-back instead of locks. A model backend may impose a separate queue, but that is resource scheduling, not a semantic ban on concurrent natlang calls. The scoped `foo.nl` loader remains, but it becomes a module/function loader rather than a whole-application runner.

## One execution model and portability fix

Today the Node and browser eval bridges use `transpileModule`, copy values through `scopeBridgeValue`, and require JSON-like `portable()` / `coerce()` data. That strips function identity and prototypes and rejects common JS values such as `Date`, `Map`, class instances, cycles, and callbacks. The root host then dumps the result. This is a poor match for TypeScript functions with closures.

Replace that boundary with a **live value bridge** inside one invocation context:

1. Keep primitive and plain data values directly when possible. Give objects, arrays, functions, folders, and captured variable cells opaque session-scoped IDs. Preserve identity, prototypes, receiver binding, cycles, and current values. Capture descriptors are getters and, for mutable bindings, setters; capture at each call, not at tag creation. A child may inspect or call a handle only through an authorized operation.
2. Separate model-visible observations from underlying values. A prompt/trace shows type, stable handle ID, and a bounded preview. `eval`/`read_value` can inspect or page large values. Never serialize an arbitrary host object just to cross from `eval` to the runtime. Do not use a JSON snapshot as the source of truth for a live closure.
3. Compile a TypeScript type into both a child prompt description and a runtime check. Reuse the current portable checker for serializable shapes, then extend validation for host objects via constructors, predicates, or structural property access through the handle. `any` and unconstrained `unknown` cannot silently become typed natlang return targets. A type string alone is insufficient validation.
4. Define the action boundary. A child reads each captured `let` cell at the start of an eval action and buffers its rebinding; on success the new value is written back, and on failure it is discarded. Write-back is version-checked: if another writer changed the cell since this action read it, the action fails with a conflict and the child simply retries its eval against the current value. No lock is held across a child call, so parallel children that only read a capture never wait on each other. Rebinding a captured `const` is a compile error. Property writes on live objects and host-service calls take effect immediately and are **not** rolled back; they are recorded as effects in the trace. Folder writes keep their transaction and semaphore semantics. A child error rejects its awaited TypeScript call, so the parent can catch it normally.
5. Keep closure-owning JavaScript in its originating realm. Model inference can run in another thread or process, but the interpreter runs in the realm that owns the task. In Studio, the owning TS task and interpreter run in the same dedicated worker, and only model turns cross the worker boundary. A structured clone is never assumed to preserve a closure or arbitrary JSO.
6. Scope handles to a task/session; release them on completion or cancellation. A retained inline callable holds its owner frame while that session lives. Durable replay of an external object requires a registered reconstruction recipe; traces record observations and effects, not a fictional portable copy. Do not promise replay for an unreconstructable object.

The shared **invocation kernel** takes a compiled lambda definition, typed positional inputs, capture cells, authority, execution context, and model driver. It creates the familiar child session and returns the checked value or throws. The old `runRoot` path ceases to be its organizing abstraction. The named `.nl` module loader feeds this kernel with its scoped callable manifest. Node and browser adapters differ only in host capabilities, filesystem implementation, module resolution, and model transport. Keep the eval implementation and prompts semantically identical across both.

The app-facing runtime owns model configuration, trace sink, cancellation, limits, services, and authority. It also owns context propagation, which both platforms implement to the same contract: a natlang call finds the task that is awaiting it.

- **Node** uses `AsyncLocalStorage`. Depending on Node built-ins in the Node adapter is fine.
- **Browser** has no native async context. The natlang compiler, which already processes every module that contains `nl` or imports natlang callables, applies an **await-restoration transform** for browser targets: each `await` in compiled code saves the current context before suspending and restores it on resumption. An async function inherits the context synchronously at its call, so context flows through ordinary compiled async code without app changes. `runtime.bind(fn)` captures the context for callbacks that run later from uncompiled code (DOM events, timers, third-party libraries). Where the native `AsyncContext` proposal ships, the adapter uses it and the transform becomes unnecessary.

A call with no resolvable context fails with an actionable error naming `runtime.run` and `runtime.bind`. Nested child calls inherit the context with narrower authority. Abort an awaited child on task cancellation, close handles, and preserve its trace. Avoid an app-visible `resume` tool or per-call `modelTurn` wiring.

## Effects and host services

Today, effects come in three overlapping forms: an untyped `host` global used by crisp modules (`host.wiki.prepare(...)`, the dominant form), `fx.<capability>.<op>` calls with `effects:` frontmatter declarations, and per-run `capabilities`. Replace all three with **typed host services**, which is how the code is already mostly written:

1. The app passes services when it creates the runtime or a task: `createNatlangRuntime({ model, services: { wiki, mail } })`, optionally overridden per task with `runtime.run(fn, { services })`. Services are ordinary objects with methods.
2. Callable-folder TypeScript (including `natlang.d/`) reads them with `import { wiki } from 'natlang:services'`. The app declares their types once with `declare module 'natlang:services' { export const wiki: Wiki; }`. The compiler resolves the import to the current task's service record at call time, and the agent's eval scope shows the services under a **services** heading with their declared types.
3. The runtime wraps each service in a recording proxy. Every method call is traced as an effect with a bounded argument preview and its result or failure. This replaces the effects journal and `effect-undeclared` checks; nothing needs to be declared in frontmatter.
4. Authority is the service record. A child inherits its parent's services; host code narrows authority by passing a smaller record to a task. There is no per-method policy layer: a service object that is reachable is usable.
5. `out.emit`-style streaming becomes an ordinary service or callback the app supplies. Package imports and network access in eval stay as they are today, gated by the workspace configuration.

## Compiler, build, and editor

The natlang compiler is the authoritative build/check path for files containing `nl`:

1. Build a TypeScript `Program`/`TypeChecker` over the whole project, including imports and project references. `natlang build` and `natlang check` write a generated declaration file beside each `.nl` source (`foo.d.nl.ts`, used through TypeScript's `allowArbitraryExtensions`) so plain editors and `tsc` see typed `.nl` imports; these files are generated artifacts and can be ignored by version control. Find `nl` tags by resolved symbol, not spelling alone. Resolve exact English mentions to lexical symbols and lower each tag to a JS callable with live capture accessors. Infer call-site input types and contextual return target, including the enclosing natlang `result` slot. Emit source-span diagnostics for unknown or conflicting types. Treat imported named `.nl` lambdas as typed modules, and compile each named lambda's `foo/` callable manifest separately from the host project's unrestricted import graph. Give inline lambdas created by `foo.nl` **or by callable `.ts` files in `foo/`** that same manifest. Materialize the manifest as typed, nested attributes on functions and as records for TS module exports already injected into the agent scope; render the same tree in its imports listing. Resolve `.ts` and `.nl` sibling imports under `foo/`; ordinary TS dependencies remain valid, while out-of-family natlang callable references are rejected.
2. Emit normal JS, declaration files, source maps, and a stable definition manifest. Reuse incremental TypeScript compilation, invalidating a plan when its source, referenced types, or captures change. Generated plans identify source revision, position, type signature, and capture manifest. A changed codebase module is imported at its new revision for subsequent calls.
3. Ship `natlang check` and `natlang build` first; CI must run `natlang check`. Supply one build adapter for the repository's browser toolchain and one Node development path that both call this compiler. Vite's plugin API and esbuild's plugin API provide transform integration, but their ordinary per-file hooks do not replace whole-project type analysis. The core compiler is shared, with adapters feeding compiled output to those tools.
4. Provide approximate declarations for ordinary TypeScript editing, plus an optional TypeScript language-service plugin for natlang diagnostics, inferred capture/target display, and navigation. It is an editor aid: TypeScript's own documentation says language-service plugins do not run in `tsc` and cannot change its emit/typechecking. Plain `tsc` remains useful for non-natlang files, but it is not a complete checker/build for a project using this extension.
5. Make the compiler work for packages, aliases, monorepo references, watch/HMR, browser builds, and Node ESM. Specify versioned compile output so a package cannot silently run source compiled by an incompatible runtime. No runtime evaluation of raw `nl` text as a fallback if a file missed the transform.

The present scope `eval` compiler should use the same type/plan machinery. TypeScript source files and agent-authored `eval` are two front ends to the same kernel, not separate natlang languages. Keep the existing iterative `eval` and `console.log` observation behavior inside interpreted lambdas. Arbitrary host TS code uses the project's normal compiler and runtime.

### Constrained TypeScript in a natlang callable folder

Use ordinary `.ts` files. The natlang compiler already has to identify callable folders and analyze the whole project, so it can apply an additional policy there without inventing a new file extension or changing TypeScript syntax. `natlang check` and `natlang build` enforce it; plain `tsc` and an optional editor plugin cannot stand in for that build gate. Apply the same policy to TypeScript authored in a lambda's persistent `eval`. Ordinary application `.ts` files outside a callable folder are not subject to these restrictions, even when they contain an inline `nl` expression; the inline child itself is.

1. **Allow only finite iteration forms.** The checks are mostly syntactic, so they run without a type checker, which keeps per-eval compilation cheap: forbidden forms are rejected by the parser pass, and array-only iteration is enforced by a runtime guard rather than by static types (project builds may additionally report a static diagnostic when the checker proves a non-array source). Reject `while`, `do ... while`, `for ... in`, general `for await ... of`, generator functions/`yield`, `for (;;)` and other open-ended or noncanonical `for` forms. Accept a counter `for` only when its initializer, bound, and step resolve to a monotone finite range whose counter/bound cannot be reassigned in the body; diagnose anything the checker cannot establish. Accept `for ... of` whose source is verified at runtime to be a native array with the built-in iterator, guarded against growth beyond the length observed on entry. Reject iteration of arbitrary `Iterable`/`AsyncIterable` or repeated `.next()` consumption in constrained source. Keep built-in finite array methods such as `map`, `filter`, `reduce`, `find`, and `some` when the receiver and method are verified; apply the same recursion policy to their callbacks. Review spread and `Array.from` sources so an unknown or infinite iterator cannot hide in a one-line expression. The sole open-ended exception is a branded `iterateOn(...).streamUntil(...)` result with progress review. This is a deliberately conservative source-language policy, not a general proof that every accepted program terminates.
2. **Build an authored-call graph.** Give each `.nl` definition, inline `nl` definition, and authored TS callable a stable ID. Include function declarations and expressions, arrows, methods, getters/setters, constructors, and exported record members. Resolve calls through TypeScript symbols, sibling imports, aliases, and statically known property paths. Use strongly connected components to reject direct and mutual cycles, and report the source spans and cycle path. The existing file-loader cycle check is useful but insufficient: `a.ts` can call `b.ts` and vice versa without cyclic source imports.
3. **Guard dynamic paths.** Instrument entry to authored TS callables and natlang lambdas with the same per-task active-call set. A second entry to an already-active ID fails before executing its body, including when reached through a callback, function value, dynamic property, or an imported sibling. The guard is task-local, so separate concurrent tasks may call the same function. This catches recursion that static analysis cannot prove; it does not ban higher-order programming by default.
4. **Bound the guarantee.** Reject `eval`, `Function` construction, and untracked dynamic module loading from constrained source, and do not permit a live handle to replace an authored callable with uninstrumented code. External libraries may implement their own recursion internally; the guarantee is that the Natlang folder's authored functions cannot reenter themselves or each other. Host application TypeScript remains unrestricted. If a foreign callback reenters an authored function, the guard still catches it.
5. **Make edits safe.** Re-run the checks on a codebase content edit before publishing it. Invalid edits leave the previous version live. Both Node and browser use the same diagnostics and guard. Update agent-facing errors and the authoring skill with accepted finite-iteration patterns, rejected obscure loop forms, and a clear mutual-recursion example.

The name `.ts` is sufficient because this policy follows the callable-folder boundary. A dedicated extension would only be warranted if the same file needed incompatible meanings depending on who imported it; the plan instead compiles one restricted module artifact for that folder. Do not claim to prove total termination of JavaScript: a called external library, effectful getter, or asynchronous host API may run indefinitely. The promised guarantees are no recursion through authored Natlang-folder callables and no unchecked open-ended iteration in their source, backed by static rejection and runtime entry/iteration checks.

The sanctioned open-ended exception is [`iterateOn`](ITERATE_ON_PLAN.md): every natlang callable exposes `.iterateOn(initialState, ...fixedArgs).until(donePredicate)`, with the free `iterateOn(step, initialState, ...fixedArgs)` form sharing the same implementation. It replaces the current Iterate node (Map and Fold are removed in favor of plain TS) and provides checked state transitions, optional progress streaming, stable call-site identity, optional persisted duration/step statistics, and increasingly frequent natlang progress reviews. A typed `streamUntil` result is the one permitted `for await` source inside constrained callable-folder code; arbitrary async iteration remains prohibited.

The accompanying [training-data plan](INLINE_NATLANG_TRAINING_DATA_PLAN.md) covers inline-lambda decisions, observation-driven follow-ups, logical proofs and abduction, large relational worlds, reactive actors, adaptive iteration, and honest failure trajectories against this compiler/runtime surface.

## Host, package, and app refactor

**Host SDK.** Replace the root request shape in `ts-host/src/native/host.ts`, `ts-host/src/browser/host.ts`, `ts-host/src/browser/client.ts`, `ts-host/src/native/runtime.ts`, and the Node/browser environment bridges with context creation, inline invocation, live handles, and the shared kernel. Factor common request/agent setup once; remove duplicated root parsing and browser's `as never` environment cast. Replace the flat helper construction in `ts-host/src/scope-compiler.ts` with typed callable objects carrying nested child properties; update `ts-host/src/native/agent.ts` to render that hierarchy in the existing imports listing. Make `read_function`, `edit_function`, and diff references accept the same dotted child paths so the agent can inspect or edit what it can call. Retain a single typed trace/result contract. Expose model transports as configuration; allow a task to select its model without embedding transport arguments in every call.

**Application adapters.** Refactor `ts-host/src/terminal/application.ts`, `ts-host/src/browser/application.ts`, and Studio's runner/worker code into ordinary TypeScript application code. A reducer or view may still be a useful application function name, but it is a TS callback that calls `nl` when needed, not a special run mode. Preserve the current event queue's commit/view retry and deduplication guarantees in a small generic utility where apps need them; keep `BrowserDomRenderer` or other rendering utilities independently of natlang execution. Browser workers must preserve capture ownership as described above. Simplify manifests in `ts-host/src/package/` and `spec/package-manifest.schema.json` to point to compiled TS entry modules and authority, then update the CLI. Keep packaging security checks and package pinning. Migrate `NativeSourceWorkspace`, playground, browser-local, direct CLI runners, and teacher/research/conformance callers in the same cutover so none silently retains a root execution path.

**Examples and corpus.** Refactor `examples/triage`, `examples/npm_app`, `ts-host/examples/browser-board`, Studio's generated programs and research app, and all shipped `codebases/*` applications. Keep named `.nl` lambdas and their `foo/` callable folders where that scoped authoring model is valuable. Migrate each application's entry, state wiring, and host calls to TypeScript; add inline `nl` calls where semantic work naturally appears in host code. Crisp modules become ordinary TypeScript with sync or async implementations, named exports, and record exports as appropriate; their placement under `foo/` still controls which named lambda may call them. Rewrite app scaffolds to show inline calls in handlers, libraries, callbacks, and ordinary business logic. Update generators/materializers so new apps emit TS entry modules and scoped named `.nl` modules when needed. Do not hand-edit generated Studio copies without changing their generator. ## Known implementation risks and chosen defaults

- **Type inference:** use the TypeScript checker plus natlang constraints; reject ambiguous targets with a local diagnostic and allow `nl<T>` as an explicit escape hatch. Never infer the target from the child's output.
- **Portability:** keep live values in the owner realm; use handles/RPC only when crossing a worker or process. Do not pretend structured clone or JSON supports arbitrary closures.
- **Effect atomicity:** captured cells commit with version-checked write-back; live-object property writes and service calls are immediate, traced, and not rolled back. Folder reduction keeps its existing semaphore semantics.
- **Authority:** an inline natlang function receives its creating task's services, folder/codebase authority, and the values it captures. Capturing or passing a live object grants its full method surface; there is no separate per-method policy.
- **Callable scope:** a named `.nl` lambda and its inline descendants see the same callable items under its companion folder. These already-injected functions expose descendants as typed attributes and appear as a hierarchy in the agent's imports listing. Callable `.ts` items can import `.ts`/`.nl` siblings and create inline natlang lambdas with that same context. The compiler's import graph cannot broaden that namespace, and runtime checks reject forged or aliased out-of-scope handles.
- **Recursion:** reject direct and mutual cycles among authored `.nl`, inline, and callable-folder `.ts` functions at build time where visible, and at runtime when a definition appears in its own caller chain. Concurrent sibling calls and sequential reuse remain valid; foreign library internals are outside this guarantee.
- **Eval compile cost:** only an eval containing `nl` or `iterateOn` builds a checked program; other evals keep the fast parse-and-transpile path. Library `SourceFile`s are cached across evals.
- **Host-object targets:** check built-ins such as `Date` or `Map` by their internal tag rather than `instanceof`, because eval runs in a separate `vm` realm; check user classes with `instanceof` in the owning realm. A child can return a class instance only when the class is reachable from its scope; otherwise the compiler asks for a portable target type.
- **Loops:** allow only checked finite iteration in callable-folder TS and lambda `eval`, with runtime iteration guards; `iterateOn` is the sanctioned monitored open-ended operator. Ordinary TS app modules remain unrestricted.
- **Build adoption:** require the natlang compiler for `nl` files and fail loudly when it has not run. Editor integration cannot substitute for that compiler.
