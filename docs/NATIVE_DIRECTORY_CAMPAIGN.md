# Native directory improvement and optimizer distillation

This campaign tests whether an ordinary natlang optimizer can diagnose and redesign partially working programs. Luna executes the optimizer; Bonsai executes the target programs. The default source remains one diagnosis-and-edit directory reducer, called through the authored lifecycle and `folder.iterateOn`. No special tool filter, replacement runtime prompt, compatibility mode or language gas system is added.

The four development families exercise final refund decisions over nested files, invoice/decision joins by ID, exact sequential file edits, and deduplication of revised reviews. Two transfer families exercise authorized training exceptions and final confirmed meeting assignments. Each starting program implements the easy case; each family has three train folders, one validation folder and two sealed confirmation folders. Fixtures preserve unrelated files and compare exact output text. Reference source stays hidden from the optimizer. These are independently specified reconstructions of observed failure mechanisms, not falsely labelled historical student failures.

Structural editing may change the root `.nl`, introduce child callables, reorganize companion helpers, or replace a poor helper with direct batch judgment and exact bookkeeping. Allowed helper paths live under `solve/`, the callable companion folder. The editor's first compact card now includes the previous candidate's changed helper source and actual diagnostics. It can formulate a different experiment without reprinting the entire request. The language's ordinary tools and typed source/state ownership remain in force.

`build-directory-campaign.mjs` builds and compiles every source/reference. Execution tests verify that all six starting programs pass their simple folder with independently supplied semantic labels. `run-directory-campaign.mjs` freezes the SDK and optimizer source, runs probe/native/direct/confirmation arms sequentially, then replays and exports complete loops automatically. A failed family does not gate later work. One overall allocation permits 2,400 model requests, 520 case executions and six elapsed hours. Native search has three experiments per program. One helper-layout fixture correction preserves its four model requests, one case execution and original elapsed clock; it does not reset the allocation.

The first live refund probe passed its simple baseline case but recorded harder-case timeouts, including two reference timeouts. These are operational failures and cannot substantiate semantic headroom. Their traces remain available to optimization; no reference-headroom claim is made for that family at this checkpoint. `summarize-directory-campaign.mjs` separately reports quality, cost, changed source paths, multiple accepted experiments, recovery after a rejected experiment, confirmation and training admission.

Training admission now distinguishes a successful file-tool operation from a successful source experiment. An edited child whose measured proposal was rejected remains failure context rather than a positive SFT target. Historical loop artifacts and provider observations are retained. This refinement leaves 40 positive turns from the original cohort and 33 from the fresh file repairs, with the other 39 previously exported turns retained as rejected-edit evidence. All admitted invocation contracts remain independently replayed. These are source-admission changes, not discarded historical observations.

### Expanded general optimizer curriculum

`build-training-slate.mjs` creates 192 native source-optimization tasks: 12 variants in each of 16 families, with 960 independently labelled folder cases. Families cover urgency, explicit consent, completed delivery, active licenses, cancellation, recommendations, authorized access, support resolution, attendance, renewal, identity joins, latest revisions, ranking, exact multi-file edits, corrected extraction and semantic routing. Each task starts with a compiled partially working directory reducer and companion helper. The optimizer can edit these files and add child callables through the ordinary native improvement program. Cases vary identifiers, amounts, scores, record counts and nested paths; exact effects require preservation of unrelated files and whitespace. Gold labels and reference source are hidden from execution. These are fresh reconstructions of failure mechanisms, not claimed historical reproductions.

The reproducible slate is stored at `data/teacher/self-improvement/task-slate-v1/`, with its seed, family inventory and content hash. It contains tasks and gold oracles, **not positive SFT demonstrations**. All cases are development cases: three training and two validation folders per task. The existing sealed confirmation and transfer cohorts are not reused.

`run-training-slate.mjs` executes the ordinary authored optimizer with Luna and the target programs with Bonsai. Tasks run serially, with three finite experiments each and a total allocation of 192 tasks, 34,560 model calls, 6,144 case executions and 192 hours. Each task has at most one hour, 180 calls and 32 executions. Resumption retains completed outcomes and each task's allocation journal. No task failure blocks the remaining slate. Replay uses the pinned SDK, and independent source admission precedes publication. Original traces, rejected attempts and per-task admission receipts remain available. Verified turns publish after each task; the final corpus output also includes earlier admitted optimizer decisions.

New general production recipes include `build-optimizer-curriculum` and `generate-optimizer-curriculum` by default, before dataset preparation. Preparation explicitly consumes the resulting verified turns alongside other producers' data. The default is all 192 tasks; `--self-improvement-variants` changes the finite collection size, while optimizer provider/model flags select the teacher. Already frozen recipes keep their inputs. This generation lane does not change the separate Sharp pilot's declared dataset or sealed evaluation.

The live large-slate controller is queued at `runs/optimizer-training-slate-v1/generation/` behind the current directory campaign, then starts automatically with one worker. Its frozen runtime and progress configuration pin the source, cases and models. This scheduling avoids adding concurrent Bonsai requests during the current comparison; it does not impose a quality gate on the slate. Execution checks cover all starting programs, case diversity and absence of exposed gold labels, continuation after task failures, and inclusion of generation outputs in the general preparation recipe.
