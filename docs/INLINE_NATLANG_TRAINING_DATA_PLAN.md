# Ancillary data plan: inline lambdas and observation-driven follow-ups

This plan accompanies the [TypeScript integration plan](TS_INLINE_HOST_INTEGRATION_PLAN.md), [inline lambda design](inline-natlang-lambdas.md), and [`iterateOn` plan](ITERATE_ON_PLAN.md). Its purpose is to teach the interpreter model to create typed inline natlang lambdas when a semantic subtask belongs in code, to use the callable and iteration surfaces correctly, and to **run code, inspect real results, and make a subsequent decision** when the result matters. It also supplies authoring examples for agents writing ordinary TS applications. **Assume the specified TypeScript compiler, Node/browser runtime, live closure and handle semantics, scoped imports, typed child calls, proof/observation adapters, shared IR, and `iterateOn` are implemented and functioning.** This is a data construction plan for that system, not a protocol readiness experiment.

Implementation status, the case format, the family catalog, and pilot findings are in [INLINE_CURRICULUM.md](INLINE_CURRICULUM.md).

## Existing evidence and the gap

The existing [semantic follow-up probe](semantic-followup-examples.md) has 96 cases. In its small Bonsai pilot, 10 report cases and 6 composite cases were accepted; the composites used 3–6 `eval` calls. The [read-before-code probe](READ_BEFORE_CODE_PROBE.md) has 59 cases; its first eight-case pilot read needed files or values before implementation, but seven of those eight still used only one `eval`. These are useful seeds, not sufficient coverage of inline lambdas or observation-driven revision. The read-before-code probe also exposed a real paging mistake and ambiguous oracle wording. Treat those as generation and admission lessons, not as training successes to copy wholesale.

The desired behavior is causal, not a tool-call quota. A valid follow-up case must have at least one decisive observation unavailable in the opening. At least two plausible next actions must exist before that observation, and the observed content must change which action is correct. A task that can be solved by a single fixed TypeScript `if` over already visible fields is an ordinary coding sample, even if its instructions demand two `eval` calls. Do not reward ceremonial `console.log` calls or repeated reads that convey nothing new.

## Two training surfaces

1. **Interpreter trajectory track (priority).** A model executing a named `.nl` lambda uses `eval` to compute and inspect values, creates anonymous `nl` callbacks or calls imported named lambdas, observes child results, edits existing codebase content when appropriate, and completes typed results with line marks. This matches the student interpreter's actual tool surface and must preserve the teacher's ordering, reasoning, actions, observations, and child calls in IR.
2. **TS authoring track.** A model writes ordinary host/project `.ts` code that uses `nl`, imported `.nl` functions, hierarchical callable attributes, directory reducers, and `.iterateOn`. Compile and execute the result in a fixture app. Keep these rows tagged as authoring tasks; only mix them into interpreter training when the student actually sees that file-editing surface. Otherwise use them for developer-agent examples, compiler tests, and future authoring training.

For the interpreter track, generate both **single-call** examples, where one well-formed `eval` containing inline lambdas is the right answer, and **genuine follow-up** examples. The new architecture should not force several turns when the decision is already known. Conversely, do not collapse a hidden semantic observation into a precomputed fixture in the prompt.

## Corpus scale and balance

Build toward at least **10,000 distinct source programs**, **40,000 varied execution cases**, and **50,000 admitted model-decision training rows** across at least **40 task families**. These are planning targets, not a license to admit low-quality repetitions. Freeze each reviewed shard independently so teacher collection and training can use completed shards while generators continue discovering new applications. Start with a few hundred end-to-end cases to inspect data quality and IR rendering, then scale by adding independent workers and batching independent model requests. Do not batch dependent turns within one trajectory.

Make reasoning in worlds the largest domain share: aim for roughly **30% logical inference, proof, and abduction**, **25% relational knowledge and graph investigation**, **20% reactive world or actor control**, and **25% other applications and formal interface coverage**. These are orthogonal to the behavior slices below: a relational proof task may exercise inline lambdas, several observations, and `iterateOn` at once. Count actual admitted cases, including difficult failures, rather than generated prompts.

Target rough execution balance, measured after admission rather than only at generation:

| Slice | Share | What it should teach |
|---|---:|---|
| Inline lambda placement, capture, and contextual types | 25% | Choose semantic boundaries and generate valid `nl` with inferred `T`, inputs, and closure names |
| Observation-driven `eval`/read/follow-up | 30% | Read or compute first, interpret the observation, then revise code or choose a next action |
| Nested calls, scoped imports, hierarchical exports, and live values | 15% | Use the actual callable tree and JS value identity without invented paths |
| `iterateOn` and progress review | 15% | Step/check distinction, fixed args, streaming, useful persistence, divergence handling |
| Folder reducers, codebase edits, failures, and recovery | 15% | Scoped file authority, valid edits, checked returns, honest errors, and caller recovery |

Within each slice, vary codebase sizes, state/result types, source wording, import-tree depth, input size, model visibility, and application domain. Keep substantial quotas for zero-step completion, multi-step completion, genuine blockers, and errors. Track the **number of meaningful observations and revisions** separately from token length; most training rows should be small decision segments with the current state and optional notes, never a pasted prior conversation.

## Inline-lambda task families

Create at least several hundred **program shapes** across these families before multiplying inputs. Every shape needs a typechecked expected behavior, several semantically different input variants, and at least one held-out wording/source layout. Use typed callback contexts so the compiler can prompt children with the inferred target before generation.

| Family | Representative task | Main trap or capability |
|---|---|---|
| Immediate semantic return | A typed `Verdict` assignment from an awaited inline `nl` call | Infer `Verdict` from the awaited assignment; avoid `any` or post-hoc type guesses |
| Typed callback argument | Pass `nl` directly to an async `reviewEach`/`mapAsync` helper | Infer callback input and promised return; avoid sync `Array.filter` misuse |
| Parent `result` context | `result = await nl`...`(item)` inside a named lambda | Child target comes from the enclosing result slot |
| Captured policy/threshold | Mention exact `policy`, `threshold`, `folder` names in prose | Capture only visible names; distinguish callback argument from closure |
| Late binding and shadowing | Reassign a `let` before invoking a saved `nl`; shadow another name in a block | Read the call-time lexical value and correct symbol |
| Multi-capture inference | Decide from two computed metrics and one prose policy | Produce a semantic inference from combined eval values, not a single field test |
| Generic/union targets | Callback under a typed generic helper or union result | Resolve a unique target or report a source diagnostic; use `nl<T>` only when needed |
| Parallel independent children | `Promise.all` over separate semantic judgments | Preserve input/result association and safe concurrent capture behavior |
| Stateful JS values | Capture `Date`, `Map`, class instance, method receiver, cyclic object | Use live handles and typed checks rather than JSON flattening |
| Hierarchical callable tree | Call `analyze.score`, `analyze.review.revise`, and TS named/record exports | Match the injected imports listing and source structure |
| Inline from scoped TS | `.ts` sibling imports `.nl`, then creates its own `nl` | Inherit the same `foo/` callable context without importing out-of-scope lambdas |
| Directory reducer child | Use `folder.apply(reducer, ...)` after semantic choice | Commit folder changes and typed result under the folder semaphore |
| Compiler rejection | Ambiguous target, illegal capture, reserved child name, recursion, forbidden loop | Diagnose precisely; agent changes source rather than inventing a runtime workaround |
| Error and honest opt-out | Child cannot satisfy target or evidence is missing | Report error/blocker and let caller recover; do not fabricate typed output |

Generate both cases where inline `nl` is the best design and near-neighbor cases where ordinary TS computation or an already imported `.nl` function is simpler. The decision to **not** make a new child is part of the skill. Do not reward gratuitous lambdas.

## Read, run, inspect, follow-up families

Each family below must be built as a pair or triplet sharing the same visible request but differing in hidden observation, so a canned first answer fails at least one variant. Hidden observations may come from `eval`/`console.log`, `read_value` pages, file reads, a called helper, a child lambda result, or a compilation/runtime error. The agent's later action must depend on interpreting them.

1. **Computed facts change a semantic conclusion.** Compute cohort rates, test coverage, or a reconciliation delta; inspect them; then apply a prose policy to decide support, contradiction, or uncertainty. Make aggregate and subgroup conclusions disagree in some variants.
2. **Policy loaded after computation.** First measure a result, then read a policy file or imported helper that defines the threshold/exception. Pair policies that imply different actions for the same numeric result.
3. **Counterexample after a candidate.** Run a provisional algorithm on a small batch, inspect a later counterexample, then change the algorithm and rerun. Include a nearby variant where the original algorithm was right so the model learns warranted persistence.
4. **Code/contract diagnosis.** Read an imported TS module's source, run a failing example, inspect actual output and stated contract, then decide whether to edit the helper, its caller, or the test expectation. The error name alone must not reveal the answer.
5. **Paged values with late decisive rows.** Put the crucial entry beyond the opening preview and on a later page; require correct `next start` navigation. Vary whether the late row reverses, qualifies, or confirms the initial hypothesis.
6. **Folder evidence and scoped edits.** Read existing `criteria.md`, `data.json`, and a TS helper; compute a candidate; inspect its output; edit only existing codebase contents if the helper is wrong. Keep folder `commit` separate from codebase edits.
7. **Semantic conversion after exact aggregation.** Aggregate raw events in TS, then ask an inline child to infer intent, cause, or risk from several aggregates and notes. Ensure the conclusion is not a Boolean expression over visible numeric fields.
8. **Child result changes parent plan.** Construct/call an inline `nl` analysis; inspect its typed result; then choose a different helper or file edit. Pair a variant where the child says “insufficient evidence” and the right action is a blocker or more reading.
9. **Error-directed repair without fudging.** A compiler diagnostic, failed eval, or checked-return error identifies a real source mistake. The model inspects it and fixes code when authorized; when the instructions themselves are impossible, it reports the failure instead. Keep local validation feedback policy explicit.
10. **Live object follow-up.** Inspect a `Map` or class instance through the handle API, call a method with preserved receiver, then write code based on the observation. Include reference-identity and mutable-capture cases.
11. **Application event sequencing.** Read state, event, and prior revision; call semantic reducer or view; inspect output and persistence receipt; retry a failed view without rerunning the committed event.
12. **Scoped module discovery.** Read the hierarchical imports listing, inspect a `.ts` module's named/record exports, call the right leaf, then handle its returned evidence. A flat-name guess should fail.

Make each case's *minimum sufficient sequence* explicit in oracle metadata, but do not show that metadata to the teacher. Record whether reading, computing, inspecting, or follow-up was necessary for correctness. Some correct trajectories may combine several reads or computations into one `eval`; admit them if they truly saw the decisive observation before the semantic choice. The observable causal order matters more than a fixed count of calls.

## Logic, world knowledge, and relational evidence curriculum

Build **situated reasoning programs**, not isolated answer questions. A case supplies a typed goal, access to a world or evidence store, and enough callable operations to inspect, query, test a hypothesis, construct a proof, or act. Its decisive facts are often outside the opening preview. The model must decide which operations to run, interpret their results, and either finish with a justified typed value or say what cannot be established. Use ordinary TS for exact joins, arithmetic, indexing, and proof-checker invocation; use inline or named natlang lambdas for interpreting language, choosing relevant evidence, judging explanatory adequacy, and making decisions that a fixed TS conditional cannot encode faithfully.

Keep three evidence categories explicit in every oracle: **world assertions** (facts/rules supplied by the task), **retrieved observations** (query or action results), and **background knowledge** (commonsense or domain knowledge used to bridge them). A model must not silently replace a stated world rule with a usual real-world rule. Vary whether the task uses open-world, closed-world, or explicitly defeasible semantics. Include unknown, contradictory, exception, and changed-over-time outcomes. Record which assumptions a conclusion depends on. This prevents training “plausible answer” behavior where a proof or uncertainty is required.

Create these cross-cutting families, with paired worlds in which a late fact changes the correct continuation:

1. **Natural-language entailment and countermodels.** Translate quantified premises into a typed internal claim, retrieve a late exception or scope qualifier, and decide entailed, contradicted, or unknown. Ask for a witness or countermodel when applicable. Vary negation, existential scope, nested conditionals, and statements whose ordinary-world plausibility conflicts with the local premises.
2. **Proof construction and repair.** Retrieve candidate premises from a larger corpus, propose intermediate lemmas, submit a proof DAG to a verifier, inspect a rejected edge or missing premise, and repair or report unprovability. Keep proof validity, premise provenance, and answer correctness separate. Include multiple valid proofs and a tempting invalid shortcut.
3. **Abduction and discrimination.** From observations, form several candidate explanations; query evidence that would distinguish them; rank by coverage, consistency, and unnecessary assumptions; and retain uncertainty when evidence is insufficient. A proof of “if hypothesis then observation” alone does not establish the hypothesis. Include cases where new evidence reverses the preferred explanation and cases where it confirms the original one.
4. **World-knowledge bridges.** Combine explicit graph or document facts with a small semantic inference such as whether an event could cause a later condition, whether a policy exception applies, or whether an entity can perform an action. Require the model to state the bridge premise or label it as an assumption; do not grade unsupported commonsense as a theorem.
5. **Large relational investigations.** Query a graph or table store through paged typed APIs: multi-hop joins, qualifiers, temporal relations, negation under declared semantics, grouping, counts, argmax, and provenance. Place decoy entities/paths near the target and decisive rows beyond the preview. Hide any source dataset gold SPARQL/program from the model while using it to build an oracle. Ask a semantic child to interpret the combined query results and policy text after TS has done the exact data work.
6. **Dynamic relational worlds.** Apply events that add, retract, or supersede facts; require a new query after a change. Test stale-cache errors, valid historical conclusions, and whether a previous proof remains valid under the new snapshot. Split paired variants by world snapshot rather than by individual query.
7. **Reactive actor policies.** An actor repeatedly observes a partially visible world and selects an action under an invariant, goal, and local policy. Exogenous events, delayed effects, inventory/resource constraints, and other agents can change what is appropriate. Include legitimate revisits, dead ends, recovery, and “stop/help” decisions. A case should require interpreting an observation, not merely replaying an action list.
8. **Multi-actor coordination.** Give actors different permissions and partial knowledge. One actor's action changes another's options; the policy has to avoid duplicate work or conflicting writes. Use the folder semaphore where shared artifact mutation occurs, and record wait/resume events distinctly from model hesitation. Begin with a controlled local simulator before importing worlds whose multi-agent support is untested.

**Example shapes.** In a proof task, a claimed exception lies on page three of a fact store: the agent searches, proposes a proof, sees the verifier reject a lemma, reads the exception, and returns `unknown` with the failed dependency. In a relational task, TS computes two multi-hop candidate sets and their counts; an inline lambda reads a policy and decides which candidate qualifies, then a counterfactual qualifier flips the answer. In a reactive task, `repairStation.iterateOn(world, policy).until(goalReached)` observes inventory and machine state after each action; a newly blocked route causes a different action, while repeated travel with no new evidence triggers the progress judge. In an abduction task, two causes explain an initial symptom; a discriminating test is chosen, and the model revises its ranking after the result.

### Candidate external sources and acquisition

Acquire source data or environment code from the maintainers, pin a revision and hash, and verify **dataset and dependency terms** before storing derived training rows. Keep raw downloads in an untracked cache; commit manifests and small reviewed derived fixtures. The candidates below are inputs to *new instrumented Natlang programs*, never answer strings pasted into a prompt.

| Source | What to acquire and transform | Oracle and split unit |
|---|---|---|
| [FOLIO](https://github.com/Yale-LILY/FOLIO) | Prefer its corrected release; turn expert-written premises, first-order annotations, and conclusions into read/query/justify cases. | Truth label and formal annotation; hold out entire story IDs and paraphrase families. |
| [ProofWriter](https://aclanthology.org/2021.findings-acl.317/) | Use released natural-language theories, proofs, implications, and abductive cases for verifier-assisted proof and missing-premise tasks; locate the maintained data release from the authors before import. | Proof checker plus reviewed equivalence of alternative proofs; split by theory/world generator seed. |
| [EntailmentBank](https://github.com/allenai/entailment_bank) | Download the linked data release; turn science-fact retrieval and entailment trees into premise search, lemma selection, and proof repair. | Tree edges and entailment validation; split by question and underlying fact cluster. |
| [PrOntoQA](https://github.com/asaparov/prontoqa) | Run its generator across ontology truth settings, hop counts, and OOD configurations; add late evidence and proof-check feedback. | Generator proof and labels; split by generated theory/seed and template. |
| [Abductive Commonsense Reasoning](https://github.com/allenai/abductive-commonsense-reasoning) | Download the data-only αNLI/αNLG archives linked in the maintainer README; add discriminating observations and hypothesis revision. Avoid the combined models download. | Original plausibility choices plus reviewed evidence-based ranking; split by narrative pair. |
| [KQA Pro](https://github.com/shijx12/KQAPro_Baselines) | Download the linked `kb.json` and question/program files; expose a paged graph adapter and compose relational query results with semantic policy decisions. | Gold program/SPARQL and executed answer, kept hidden from model; split by query template, entity neighborhood, and graph snapshot. |
| [CommaQA](https://github.com/allenai/COMMAQA) | Use its compositional questions and component KBs to build applications whose callable TS/natlang specialists each expose only part of the relational evidence. | Executed multi-component answer; split by question template and underlying KB, not individual component calls. |
| [ScienceWorld](https://github.com/allenai/ScienceWorld), [ALFWorld](https://github.com/alfworld/alfworld), [TextWorld](https://github.com/microsoft/TextWorld), [DiscoveryWorld](https://github.com/allenai/discoveryworld) | Pin environment versions, install outside the repo, and wrap observe/action APIs in typed adapters. Use task variations and generated worlds for reactive actor policies, experiments, and replanning. | Environment success/invariants plus review of action rationale; split by scenario family, seed, and world layout. Pin ScienceWorld's version because its 1.3.0 ordering change can alter trajectories. |

Prioritize a small ingest from FOLIO, PrOntoQA, KQA Pro, and one interactive world, then expand the source mix. Where a source is small, use it as an evaluation template or hand-reviewed inspiration until rights and contamination checks are resolved. Preserve original train/validation/test partitions and hold out entire underlying stories, worlds, and generators. Do not train on benchmark test answers, walkthroughs, gold programs, or proof text that the student might later be evaluated against. Record source URL, revision, checksum, original split, transform version, world/seed ID, and derived case IDs in an acquisition manifest.

## Adaptive-iteration and monitoring families

Use the new `.iterateOn(initial, ...args).until(done)` surface, not `$iterate`. Vary the step's fixed arguments, live state type, and stopping predicate. Include:

- Initial state already done (zero steps), ordinary 1–3 step success, and longer useful progress.
- A repeated state that indicates genuine stagnation; a repeated state that is legitimate because new external evidence arrived.
- Oscillation among plausible designs, low-quality repeated edits, and a fundamentally impossible target. The progress judge should return `divergent` with a reason.
- A run beyond `mean + 1σ` that is genuinely improving. The judge should affirm continuation instead of treating statistical unusualness as failure.
- The same call site across varied inputs, optional persisted statistics, source revision/model-cohort changes, and explicit site-ID migration.
- `streamUntil` consumed by a UI or parent lambda; early consumer cancellation; directory reducer steps with serialized folder writes.
- Step return-type failure, stopping predicate failure, progress-judge failure, and caller-side recovery without fabricated state.
- Proof search that adds verified lemmas to a theory until the goal is proved, refuted, or genuinely unresolved; its step function can choose a new premise or repair a failed derivation.
- Abduction that cycles through hypotheses and discriminating tests while retaining competing explanations; `until` checks explanatory adequacy and evidence sufficiency, not merely whether a hypothesis was produced.
- Relational investigation that expands a frontier of entities and queries qualifiers until sufficient provenance is gathered; an unusually long but shrinking frontier should continue.
- A reactive actor whose step reads the latest observation before choosing an action; its stopping predicate checks the actual world, while the progress judge distinguishes a useful revisit from a loop.

Do not train only on tidy short loops. Preserve every step/check/review in IR, including judge reasoning and the basis for continuing. Synthetic reference trajectories can cover the formal method/type/event protocol; use teacher samples for semantic progress judgments and for deciding when to persist or stop.

## Generation, admission, and IR

**Program construction.** Extend the synthetic IR generator and the semantic/read-before-code builders with versioned families for the TypeScript compiler surface. Generate source first, typecheck it, then vary inputs/hidden evidence independently. Add source adapters that turn acquired theories, graph neighborhoods, and interactive worlds into typed TS applications with data access and evaluator APIs. Use real application motifs from Studio and `codebases/*` (incident triage, evidence reconciliation, code review, rollout, notebook research, media workbench) but change policies, source layout, and labels enough to avoid copied solutions. Add a small hand-authored reference set for cases whose semantics cannot be reliably judged by a deterministic oracle. A teacher may propose additional program shapes, but a separate reviewer admits them before they become seeds.

**Oracles.** Give each case independent expected behavior and evidence provenance. Exact returns can use executable references and invariants; semantic decisions need a reviewed rubric and counterfactual paired variants. For logic, store proof obligations, allowed assumptions, countermodels, and a verifier result; do not equate a correct label with a valid proof. For abduction, score whether hypotheses explain the observations, survive the discriminating evidence, and avoid unsupported certainty. For graph tasks, execute the hidden reference query against the pinned snapshot and compare provenance as well as answer. For actor tasks, record world success, safety invariants, resource use, and the state changes that justified each revision. File edits need expected patch constraints, source compilation, and functional tests. For follow-up, validate the required causal observation and later choice, not a mandated number of tool calls. Quarantine ambiguous cases and unexpected alternative valid solutions for review. The 2026-09-23 incident-note ambiguity in the older probe is a concrete reason to do this.

**Collector.** Make teacher generation interruptible/resumable with one atomic result per case, stable case IDs, content hashes, and per-case retry state. Re-scan source manifests between work batches so newly generated applications are picked up without restarting the whole collection. Batch independent inference requests subject to GPU/model-server capacity; never interleave the dependent steps of one case in a way that corrupts its context. Preserve interrupted work only as resumable journals; if it cannot be resumed, mark it for a clean retry and remove stale partial output after replacement. Keep model/configuration/runtime revisions in provenance.

**Shared IR.** Represent the parent choice to construct an inline lambda, source span and inferred signature, capture names/versions, called child ID, raw teacher reasoning, tool calls and outcomes, eval observations, source/file reads, codebase edits, line marks, continuation notes, typed return, and caller recovery. Add source/world/snapshot IDs, retrieved fact and graph-edge provenance, assumptions, candidate hypotheses, verifier submissions and feedback, actor observations/actions, and exogenous events. For `iterateOn`, also record site ID, step/check/review events and statistic trigger. Materialize self-contained short decision segments from actual openings and current state; never paste preceding conversation into a continuation. Preserve the exact teacher choices and ordering instead of flattening everything to the final answer. Schema-version the new forms and test render → parse → replay on representative trajectories.

**Admission and balance.** Apply compiler/runtime replay, result/patch oracles, tool/result causal checks, trace/IR validation, and a sampled manual review. Maintain a rejection ledger with concrete reasons: ambiguous oracle, wrong return, invalid type target, missing observation, premature choice, fabricated file/path, unsupported handle, recursion/loop violation, invalid proof edge, unsupported world assumption, unjustified hypothesis, unsafe actor action, bad progress review, or incomplete trajectory. Deduplicate template clones and cap any family/input archetype's token share. Freeze split groups by source program, application, policy template, original dataset story/world, and paired counterfactual variants; keep all variants of one underlying problem in the same split. Measure admitted coverage by family, type, capture mode, turn count, semantic vs crisp operation, source depth, error outcome, proof depth, graph size, observation depth, and useful iteration length.

**Training/evaluation.** Feed admitted interpreter trajectories through the staged renderer and readiness audits, preserving tokenizer, split, provenance, and no-truncation gates from [the training pipeline](TRAINING_PIPELINE.md). Use synthetic formal cases before teacher semantic trajectories, and include student-failure corrections only after their behavior is verified. Evaluate held-out programs and applications with whole-run correctness plus: inline placement/type success, justified observation order, follow-up quality, codebase edit validity, honest error rate, valid proof rate, warranted unknown rate, abductive hypothesis calibration, relational provenance accuracy, actor goal/safety success, `iterateOn` completion/divergence decisions, and Node/browser parity. Compare performance by reasoning depth and world size, not only average accuracy. Never grade “used multiple `eval`s” by itself. Review actual failed traces and turn them into new paired cases for the next round.

## Deliverables and sequence

1. Versioned case schema and family catalog, with reviewed examples, proof/world oracles, and counterfactual pairs. Map them directly to the implemented compiler/runtime and IR types.
2. Source acquisition manifest and pinned small imports from the maintainers; checksums, original splits, and world IDs. Build typed graph, proof-verifier, and interactive-world adapters.
3. Generator and fixture builders for inline, follow-up, proof, abduction, relational, actor, and iteration families; source manifests that can be discovered during a running collection.
4. End-to-end smoke collection on a few hundred cases; manually inspect child/parent IR, reasoning, observations, proof/world events, and admitted SFT rows before scaling.
5. Resumable large teacher collection, independent-request batching, admission ledger, coverage dashboard, and held-out split registry. Scale until the corpus targets are met by **admitted** cases, not raw attempts.
6. Freeze reviewed shards and train the student on the new curriculum. Run whole-program and held-out application evaluation, then generate the next correction round from observed weaknesses.

The build is complete only when an agent can both write a correct inline semantic subroutine in one `eval` when appropriate **and** voluntarily inspect an observation before a later semantic or code decision when the task requires it. Successful final values without the required causal evidence do not establish the latter skill.
