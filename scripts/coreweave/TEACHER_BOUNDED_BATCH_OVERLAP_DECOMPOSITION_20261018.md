# Bounded teacher batch overlap

The production policy is: keep the existing self-hosted teacher useful while preserving every selected source, captured outcome, actual actor/runtime and closed boundary. One guardian may own at most two immutable primary batches. It may reserve the next qualified source when the older batch has no unstarted queue entries and at most six unfinished entries. A started request is never cancelled for utilization. Normal serial behavior remains the default.

1. **Observe capacity and ownership (crisp service).** Authenticate the exact guardian, each live feeder and sealed source/queue. Recompute starts/finishes from the bound per-worker journals. A low request count alone does not authorize source or owner replacement.
2. **Choose the next useful source (existing natural-language source policy).** Preserve ready-prefix, protection, exclusions and priority fairness. Count already-started reservations in chronological selection service; do not pretend an unfinished batch closed. Reserve one next packet under the existing selection lock with a durable immutable intent and per-batch start receipt.
3. **Launch bounded work (crisp mechanism).** The sole guardian owns the batch slots. Each feeder remains single-batch, with exact token/boot/birth custody. A new feeder receives its immutable source configuration path, never a mutable ambient next-source file. At most two slots exist; the existing engine scheduler still owns GPU/KV admission.
4. **Close and repair independently (existing verifiers).** Recompute each exited batch boundary, retain unfinished original obligations, and launch the existing repair protocol. Out-of-order exit never advances or rewrites another batch. Restart recovers existing token identities before any spawn.
5. **Preserve publication (crisp durability).** Export each active slot against its own immutable start/config/runtime authority and frontier. Closing an older slot does not strand its raw tail. Existing serial publisher/config behavior remains unchanged unless the explicit overlap option is set.

Qualification must cover wrong-batch and changed-source rejection, prefix/held/protection preservation, one-slot default compatibility, two-slot limit, no duplicate source selection, owner death/restart/token recovery, out-of-order completion, source-selection crash recovery, publisher per-batch custody and wrong runtime/config rejection. No model-facing prompt, sampler, serving engine or sandbox allocation changes are involved. Independent root review precedes deployment.

An already-started reservation retains its exact scheduling-policy references if later unstarted priorities are appended. Current source/protection and the retained prefix are still reauthenticated; only selection order is frozen for the real started batch. Configuration publication can recover on either side of the durable pending write and atomic source-file replacement. A guardian restart recovers the persisted feeder token even when the predecessor exits before owner publication; DRAIN prevents a fresh spawn while allowing recovery of existing work.

The feeder is the existing single-batch collection mechanism, now source controlled. Its worker/runtime/sampler/oracle commands remain shared and unchanged. Crisp additions bind the immutable source configuration by SHA/bytes, check its full source and row count, and write one durable phase/error path per batch. The guardian supplies the exact helper module root. A host-specific Python PATH is supplied only by the real-process test fixture; production retains its installed Python command.

Focused evidence covers actual two-batch archive sealing, receipt acceptance, independent durable frontiers and repeated polling; it also covers a real feeder child/token recovery, in-flight partial journal records, early next-batch completion before the predecessor, changed future priority policy, and crashes before/after source configuration publication. No held outcome or private receipt implies training admission.

Each running overlap slot also retains its SHA-bound immutable guardian configuration-history snapshot. A later declaration may change the helper for future work; it cannot relabel an existing feeder. Publication authenticates the original snapshot's control, root, teacher identity, runtime and feeder bytes, while separately enforcing the exact latest config/state revision and per-batch runtime epoch. No mutable historical path or shortened digest is accepted.

The collection repository is an explicit `collection_repo` configuration path, passed through the existing `NATLANG_REPO` environment contract. The feeder receives generation root, exact existing queue-worker path and Node bin from the guardian declaration, and uses that worker's actual parent for controller assets. Its helper module root remains separately bound to the deployed guardian source directory. Deployment must authenticate those existing source/worker/Node assets; the helper no longer embeds a developer home or assumes its own location contains worker assets.

The slot snapshots its collection repository, exact queue-worker file binding and Node directory before spawning. Restart uses that original context rather than a later config's future worker or repository. The publisher reauthenticates the original snapshot/context and actual small worker bytes; changing future helper declarations cannot silently change a started batch's execution context.
