# Qualify when shared work can use the result

Owner policy: continue useful whole-recipe SGD while readiness evidence is pending.
Do not spend a two-hour synchronous held-task window on every 1,000-update
continuation merely because a finite communication cohort has not yet been
consumed by the shared stage. Completed per-row exposure, exact current-weight
numerics and task execution remain mandatory before release and joint training.

`chooseFoundationWork(localProgress, sourceHostCandidates, previousAttempts)` is
one natural-language scheduling function:

1. Continue every model's outstanding production data using its earned
   weights, optimizer, RNG and per-row credits. Preserve the fixed foundation
   and all newer communication/ordinary obligations.
2. Advertise exact completed communication exposure as an unqualified candidate.
   It cannot release an optimizer, create eligibility, or acknowledge consumption.
3. When at least two genuine participant candidates are available, request the
   existing shared trainer's full current-weight task/runtime qualification at
   an owned update boundary. Keep ordinary asynchronous quality monitoring active.
4. Release only after the existing unchanged full readiness validators succeed.
   Failed/interrupted checks remain pending; resume useful training and let the
   supervisory policy select repair and renewed qualification explicitly.

Crisp mechanisms extend the existing trainer mode, native readiness verifier,
source-host pending status exchange and RAW stage/owned-child supervision. There
is no second trainer, queue, base-comparison gate, fake consume acknowledgement,
or historical-checkpoint qualification of current weights. The recipe selects
this policy explicitly; existing deployments preserve their old behavior until
an authenticated runtime/recipe continuation adopts the new mode.

Validation must include actual shared-trainer updates and exact checkpoint resume
while qualification is deferred; per-row candidate rejection; two source-host
candidate rendezvous triggering one real qualification request; and unchanged
full task/numerical release checks. Metadata/tiny execution tests do not claim
current trained CUDA readiness.

## Snapshot preparation and actual adoption

The policy may consume genuine qualified historical snapshots for VAE-only
preparation while each production optimizer continues useful work. It does not
label them current live weights. `snapshot_preparation: true` on the existing
complete semantic curriculum runs whole VAE exposure and structurally returns
before any joint/distill/policy backbone update. The complete downstream phases
remain mandatory and the export is never production-ready merely for preparation.

Before any backbone update, resume the same VAE/optimizer with explicit
`snapshot_adoption` (schema `natlang.native-snapshot-adoption/1`, exact bound
`plan`, and source-host `released` proof bindings in `releases`). All actual
adopted checkpoints must equal those optimizer-release proofs. The normal
full readiness validator checks each descendant. The shared trainer records
actual loaded checkpoint ancestors; only a descendant of the exact frozen
source may replace it, and only before any shared backbone update occurred.
`refresh_participants` plus declared `adaptive_refresh` then retrains every
semantic phase for those new identities, retaining the actual descendant
weights, optimizer, RNG/exposure and VAE optimizer. No forked optimizer branches
are numerically merged and no later earned SGD checkpoint is overwritten by an
old candidate. The real ownership transition happens at the adoption boundary;
there is no successful-owner waiting freeze in the RAW scheduler.

`foundation_qualification_generation` names one explicit repair attempt. The
existing pending role exchange transports authenticated per-row candidates;
two such candidates seal one request using the same trainer/owned-child path.
Failed attempts do not automatically trigger another multi-hour window next
quantum. The supervisor changes the generation after an actual repair or useful
new evidence. Independent asynchronous quality remains active separately.

## Prospective deployment fields

Use an explicit new runtime/recipe continuation, never edit frozen R14/v8.
The existing per-model RAW plan declares `foundation_readiness_policy` as
`on-shared-request` and a named `foundation_qualification_generation` (default
`initial`). Updating the generation is an operational policy change retaining
all optimizer/exposure state. The native SFT recipe stage accepts the same
policy; one-off qualification is a bound `foundation_qualification_request`
input, not a permanent refresh flag. Historical quality monitoring must have a
real external exporter/async evaluator; this trainer does not attest service
health merely from the mode name. Do not turn off a line's only quality monitor.

For preparation, both source-host plans explicitly set
`snapshot_preparation: true` and the semantic curriculum sets the same boolean.
The existing source-host relay ferries historical eligible proofs separately
from the newer pending status without rolling back owner revisions. The
semantic assets request explicitly records snapshot scope; it authorizes VAE
work only. The shared controller records `last_snapshot_preparation` separately
from `last_successful_participants` and never launches RL from a preparation.
No additional provider account, actor, queue or sandbox is introduced.

For descendant adoption, select the existing actual released proofs and their
bound role plan in `snapshot_adoption`; set curriculum
`snapshot_preparation: false`, retain its complete phase list and declared
`adaptive_refresh`, and resume with `--refresh-participants`. This is an actual
source-host optimizer handoff. A stale released proof whose role status has
since resumed/pended is rejected. The provider enumerates the exact plan,
release and current-status bindings before launch, alongside the existing
checkpoint/source/base closures. Preparation exports retain every participant
optimizer plus its source RNG and earned progress; joint training retains its
own shared RNG and VAE optimizer. No part of this prospective path establishes
that current cloud learners have adopted it or passed current CUDA readiness.

Snapshot transport has two distinct closures. The inline source-host role
attestation contains the exact old readiness, report, task, runtime and per-row
exposure evidence; its validator does not reread original recipes/cohort files.
`native_recipe_provenance` recovers that exact saved metadata without binding an
old recipe path. The legacy non-snapshot readiness path still transports recipe
inheritance and all original readiness files. Separately, the standard provider
checkpoint closure transports all *unfinished* mandatory source frames and
nested source manifests. Source-removal tests rebuild the receiver solely from
these two declared ferry inventories, then validate snapshot recipe recovery
and decode the actual Torch optimizer/RNG/carried source state. These are CPU
transport/recovery proofs, not production CUDA qualification.
