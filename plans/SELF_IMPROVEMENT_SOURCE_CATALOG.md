## Reward and provenance contract

For any optimization episode, record a host-only objective declaration such as `provenance.metric = {schema: "natlang.skill-objective/1", kind: "..."}` and, when applicable, a separate `transfer_metric`. These fields and exact bounds belong to the evaluator, not the model-visible prompt. The host must recompute feasibility and objective value from the task instance and returned artifact; it must ignore returned fields like `feasible`, `score`, `latency`, or `objective` unless verified independently.

Use a non-compensatory gate order:

1. Parse/type/build gate; malformed outputs receive no quality credit.
2. Semantic correctness gate: exact equivalence, solver check, query result equivalence, or task-specific oracle.
3. Feasibility/safety gate: constraints, resource envelope, memory safety, numerical tolerance, or required coverage.
4. Bounded quality score against a host-computed reference. Keep objective value, runtime, memory and size as separate measures when they trade off; do not invent a blended score without an explicit declared utility.

For timings, store raw repetitions and environment IDs. A speedup label without the candidate and reference being measured under the same fixed setup is not a valid reward. Do not pool CPU and GPU numbers, different GPU generations, compiler revisions, kernel clocks, or runtime cache states into one unqualified target.

Every generated or imported item should retain: upstream URL and pinned revision; exact file path and hash; file-level license expression and attribution; source/group IDs; train/support/query/transfer role; split seed; generator and reference implementation hashes; environment/hardware identity; native correctness evidence; and admission state. Heldouts must be disjoint by source/program/schema/circuit family as relevant, not merely by row. Keep failed attempts and ambiguous oracle cases in their existing failure/review lanes; they do not become SFT positives or DPO negatives by appearing in a benchmark repository.

## Implemented expansion and explicit backlog

[training/self_improvement_tasks.json](../training/self_improvement_tasks.json) pins the three expansion packets and audits. Run `python3 scripts/self_improvement_task_inventory.py` to verify hashes/counts and report absent or held artifacts. This registry tracks task preparation; [training/data_sources.json](../training/data_sources.json) remains the training admission policy. Existing games, selection and decision/compaction lanes remain separate and linked rather than counted twice.

- **90 exact optimization episodes / 1,080 cases:** weighted set cover, budgeted maximum coverage, facility location, bottleneck assignment, matrix-chain ordering and Boolean DNF minimization. Ten application families include test-suite reduction, sensor coverage, CDN placement and staffing; these aliases use the same six objectives, not ten distinct algorithms. Independent bound recomputation and role/group separation passed. Three starting libraries exercise skill creation, description tuning and irrelevant-skill removal.
- **54 code-golf episodes / 324 tasks / 18 program templates:** sequence transforms, filtering, aggregates, strings, ordering and nested-list transforms. All 5,184 reference checks passed in the pinned Python Docker sandbox. Support/query hold out program templates. v2 fixes ASCII-space/tab/LF separator semantics, with explicit CR/form-feed/vertical-tab/NBSP/NEL preservation cases. v1 is retained and excluded; it contributes no code-golf trajectories. Size credit requires every check to pass; byte size is measured after equal outer transport-whitespace trimming; a one-byte lower bound is conservative and not claimed achievable. Exact finite checks are evidence over this bounded suite, not a proof over all inputs.
- **200 KernelBench source tasks / 161 structural groups:** levels 1 and 2, revision `423217d9fda91e0c2d67e4a43bf62f96f6d104f1`, MIT attribution retained, 159 train / 41 validation tasks. AST-only preparation executed no upstream code. Numerical contracts, fresh-input correctness, compiler sandbox and isolated same-device timing/replay remain required. Both GPUs are currently occupied; no performance labels are fabricated under contention.

The remaining families are explicitly registered `executor_pending`: CPU speed/allocations, compiler/IR rewriting, lossless compression, SQL plans/indexes, cache/prefetch policies, numerical approximation, regex/parser minimization, circuits, tensor/memory layout, build/workflow scheduling, retrieval/ranking under cost, proof/program minimization and experimental design. Current Boolean DNF provides a first exact circuit-like landscape; arbitrary circuits still need their own verifier. Existing graded SQL correctness is not a query-optimization timing evaluator. Existing ranking/calibration scores are useful but do not implement a retrieval cost budget.

Next expansion order: cache trace policies and exact round-trip compression; generated SQL indexing/work-count tasks; compiler rewrite and numerical-error landscapes; isolated GPU kernel executor. Each requires an executable evaluator and role-disjoint workload families before collection. [PIE](https://github.com/LearningOpt/pie) is another candidate CPU optimization source, with correctness/performance evaluation tooling; its programs and input provenance need individual review before import. Do not treat its repository license as universal permission for all upstream submissions.

## Research-heavy semantic classification expansion (2026-10-04)

Prioritize finding and synthesizing evidence, not guessing a category from a short sentence. A task should require document retrieval, scope/date checks, exceptions or competing interpretations, and a decision grounded in specific evidence. Tune skill descriptions to select domain-specific research procedures; tune skill bodies to improve search, source comparison and decision checks. The reward landscape can expose separate verified evidence coverage and verdict accuracy, while full credit requires both.
