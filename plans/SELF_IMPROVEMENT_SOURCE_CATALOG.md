## Reward and provenance contract

For any optimization episode, record a host-only objective declaration such as `provenance.metric = {schema: "natlang.skill-objective/1", kind: "..."}` and, when applicable, a separate `transfer_metric`. These fields and exact bounds belong to the evaluator, not the model-visible prompt. The host must recompute feasibility and objective value from the task instance and returned artifact; it must ignore returned fields like `feasible`, `score`, `latency`, or `objective` unless verified independently.

Use a non-compensatory gate order:

1. Parse/type/build gate; malformed outputs receive no quality credit.
2. Semantic correctness gate: exact equivalence, solver check, query result equivalence, or task-specific oracle.
3. Feasibility/safety gate: constraints, resource envelope, memory safety, numerical tolerance, or required coverage.
4. Bounded quality score against a host-computed reference. Keep objective value, runtime, memory and size as separate measures when they trade off; do not invent a blended score without an explicit declared utility.

For timings, store raw repetitions and environment IDs. A speedup label without the candidate and reference being measured under the same fixed setup is not a valid reward. Do not pool CPU and GPU numbers, different GPU generations, compiler revisions, kernel clocks, or runtime cache states into one unqualified target.

Every generated or imported item should retain: upstream URL and pinned revision; exact file path and hash; file-level license expression and attribution; source/group IDs; train/support/query/transfer role; split seed; generator and reference implementation hashes; environment/hardware identity; native correctness evidence; and admission state. Heldouts must be disjoint by source/program/schema/circuit family as relevant, not merely by row. Keep failed attempts and ambiguous oracle cases in their existing failure/review lanes; they do not become SFT positives or DPO negatives by appearing in a benchmark repository.

## Immediate sequence

1. Expand the project-generated objective builder beyond its current three kinds with routing, cache/layout, test reduction and one continuous numerical task. Keep exact small-instance references and bounded inputs; measure no model behavior during construction.
2. Add a CPU-only code optimization lane with generated inputs and differential tests. If importing LLVM test-suite examples, begin with one individually licensed subdirectory and record third-party dependencies separately.
3. Prepare a KernelBench source/license inventory only after choosing a small set of operator files and their exact license/provenance. Then define a CUDA replay adapter with correctness first and repeatable device-specific timing second. A local code-only task may be useful, but it is not evidence of GPU performance.
4. Add generated SQL/retrieval calibration tasks using deterministic project-owned rows and a host-side evaluator. Keep BEIR and TPC-H as later evaluation candidates until individual dataset/query licenses are reviewed.
5. For circuits and external verification suites, select only a few programs with clean file-level rights and a trusted equivalence/property checker. Reject broad repository import as a substitute for provenance work.
