# Program supply, demonstrations and feature coverage

Owner clarification, 2026-10-31: distinguish executable tasks available for RL
from programs with generated SFT demonstrations. An SFT program may also supply
RL tasks. Recover older program ideas and dataset-backed feature curricula rather
than replacing their useful work with another narrow authoring campaign.

## Evidence states

Track these independently for each application and related invocation world:

- Idea/design: a proposed application, dataset and computational problem.
- Executable task: actual package, inputs, effects and independently checked oracle.
  This can supply RL without a teacher demonstration.
- Sampled attempt: actual actor/checkpoint, prompt/runtime, complete or partial
  execution graph and outcome. Failed attempts remain diagnostic or preference
  candidates; they are not positive SFT.
- Qualified SFT: verified sampled actions converted with full graph/state custody,
  current protection checks and source provenance.
- Adopted training source: an actual recipe transition and subsequently observed
  exposure. Registration or conversion alone does not establish adoption.

A program does not become unavailable for RL because it supplied SFT. Preserve
world-level held boundaries when reusing it. Historical teacher attempts never
become current-policy rollouts merely because the application is reused.

## Feature coverage is measured execution

The recovered broad task inventory reported 520 directory-reducer cases and 64
`iterateOn` cases, but zero cases combining the two. Those counts describe task
definitions, not observed successful model use. The LogHub application is being
repaired against live traces to supply a real folder reducer plus iteration,
staged reconciliation, state checks and nested semantic decisions.

For every reusable dataset/family, record which meaningful operations it supports:
folder reads/writes, reducer application and iteration, per-item awaited `nl`,
typed children, native Neuralese producer/consumer dependencies, exact code
sorting/filtering/counting, and state/effect recovery. Distinguish declared,
actually executed, successful, SFT-qualified and actually trained coverage.
Unknown execution coverage stays unknown.

Choose features because the application needs them: folder-level reconciliation,
incremental document processing, staged repairs or durable state transitions.
Do not impose one pipeline on all domains or require the model to make unnecessary
calls solely to satisfy a feature counter. Outcome RL can reward any valid solution;
positive idiom-teaching SFT additionally needs the intended useful behavior.

The bounded recovery audit now includes these older reservoirs. Its remaining
integration work is owned by the primary supervisor, alongside continued useful
training; unfinished catalogs must not be mistaken for exhausted supply.
