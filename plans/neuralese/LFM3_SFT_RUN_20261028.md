# LFM3-1.7B joint SFT run (2026-10-28)

Binding decisions: `LFM3_COMMITTED_DECISIONS_20261028.md`. Recipe: `training/neuralese/recipes/lfm3-joint-sft-20261028-v1.json`
(bound to the mixture version that seeds the run). Owner (2026-10-28): compute-heavy work is not held up by unrelated
work. Training starts with what exists; data appends, QAT, throughput and harness fixes are adopted live at safe
update boundaries, preserving optimizer, RNG and exposure.

## Configuration

- Base `LiquidAI/LFM3-1.7B@40ebe0aa` on the native port. The sandbox downloads the pinned revision from the hub
  (9 s) instead of a 3.4 GB push from DGX.
- Full backbone from update 0. MuonSR on matrices; AdamWSR on norms, conv kernels and learned rows. Profile
  `bf16-stochastic-rounding-v1`, dtype BF16.
- Learning rates: backbone 2e-5, learned rows and adapter 1e-3. Weight decay 0.1. `--lr-warmup 150` (new,
  8302e16f2: linear over the lineage's first 150 global updates; a DiLoCo learner continuing a parent past 150 runs at
  the constant rate). Weight EMA 0.999, held eval on the EMA.
- Objective: `own-outputs/1` with a 10% reasoning share and source-cohort family balance (max scale 8), through the
  mixture's CE supervision policy. Matrix telemetry every 50-100 updates.
- Data: `build_lfm3_joint_sft.py` mixture versions under `runs/lfm3-mixture/joint-sft-vN` (tier policy
  `lfm3-joint-sft-mixture-policy-v1`). These are pre-tokenized native graph cohorts plus exact packed geometry, so
  learners do no tokenization. Held/dev data never enter the train manifest.
- Throughput: plain cotangent backend and compiled layer pieces (24225f416, default), chunk 1024, 32k tokens per
  update.
- QAT (FP8 0-0.15, NVFP4 0.1-0.5): native-trainer wiring in progress. It is adopted at a boundary when it lands, with
  the ramp position carried by progress.

## Measurements

Provisional sandbox check (`lfm3-sft-check-20261028c`, sandbox b6873d56, RTX PRO 6000 Blackwell 97.9 GB, 2 CPUs,
64Gi cgroup). Code at the pre-plain path with `device_fp32` cotangents, 1,966 provisional LFM3 graphs, legacy row
weights:
- 4.8 s/update at ~32k tokens, 6.6-6.8k forward tok/s. GPU utilization 98-100% in samples, so 2 CPUs did not starve
  it.
- GPU used ~20.5 GB; torch peak allocated 15.1 GB.
- Host RAM 8 GB steady, 16 GB after held eval, peak 26.8 GiB around the end-of-stage save and reload.
- Full-state checkpoint 12.26 GB.
- Loss 2.78 at update 1, 0.92 at update 62.
- Learned interface rows moved 1-1.3% by update 50; backbone matrix norm ratios were 0.99998 (warmup).
- The adapter `up` stayed exactly 0 because the provisional data has no Neuralese graphs.
- Rerunning the finished stage restored and exited cleanly. The mid-run SIGTERM, restore and continue path is checked
  in the seed run.
- First attempt failed on held rows labelled `train`: the trainer requires `split: test` for held.

Real-mixture check (seed sandbox fd495bc4, joint-sft-v1 = 338 rows, own-outputs/1, plain backend + compile at
24225f416, 32k tokens/update, 10 epochs, a temporary group-disjoint held set of 256 provisional rows since v1 held is
empty):
- 200 updates at a median 2.57 s/update, 12.3k forward tok/s. CUDA peak 20.9 GB. Host cgroup peak 16.5 GiB.
  Startup to the first update took about 20 s.
- Reply CE fell from 1.49 (update 1) to 0.02-0.03 (updates 198-200). Reasoning CE fell from 3.74 to 0.10-0.15. This
  is training-set CE over 10 epochs of 338 rows, so it shows real learning and memorization, not generalization.
  Held CE on the unrelated provisional set ended at 2.85.
- Learned sparse rows got real updates (e.g. token 124901: 425 of 2,048 elements changed in one update, nonzero
  gradient).
- SIGTERM at update 102 (after the update-100 checkpoint): saved, exited 0, restarted with the identical command,
  restored in 25 s and continued from global step 103 to 200. No step was duplicated or skipped.
- File-system snapshot of the seed volume: READY within seconds (4.08 GB).
- Download from a sandbox to DGX: 9.15 MB/s (200 MB in 21.9 s). A 12 GB full state therefore takes about 22 min.

Decision (2026-10-28): the v2 mixture build gates 4 GPUs, so its units run at ledger priority medium instead of low.
Coordinator decision: the LFM3 teacher twins were rendered with the full system prompt, but serving uses
program-header prompts. They are re-rendered first and appended later; the first DiLoCo data excludes them.

Transport finding: DGX uploads to sandboxes run at 0.2-0.5 MB/s over Wi-Fi (`wlP9s9`; the Ethernet `enP7s7` has no
carrier). A 50 MB wheelhouse took 220 s and the 69 MB code archive 141 s. So nothing large is pushed from DGX:
- the base comes from the hub;
- the DiLoCo parent is made in the cloud (seed sandbox) and reaches the coordinator and learners as a restored volume
  snapshot of the seed's `/work`;
- a running sandbox is reused (`scripts/coreweave/hold.sh`, `push_files.py`) rather than relaunched.
DGX-side recovery copies of 12 GB full states depend on the download rate, which is not yet measured.

## Sizing

- Learner RAM minimum: 48Gi (measured 26.8 GiB peak +25%, rounded up for the save buffer).
- `local_steps` 128: 128 x ~5 s = ~10 min per round. Transfer per learner is 3.4 GB of BF16 pseudo-gradient up and
  the merge down, overlapped with compute. It is confirmed against the 5% rule once round 1 is measured.
