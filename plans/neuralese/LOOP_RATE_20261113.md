# Held-v2 loop rate 0.037 -> 0.061 on the base: wall-clock accounting and noise, not a harness loop (2026-11-13)

Question: the base 5ff07638 measured on held-v2 (256 x 2) on the GRPO actor under two harness commits shows loop_rate
0.037 (old series c33dee66a4b7, pin 17f1866c2, 19 looping episodes) vs 0.061 (new series e3a1066c7874, pin 37c221bfe,
31). Results: `ops/grpo-v1/run2/held/step-00000-series-c33dee66a4b7/` and `.../step-00000/`.

**Definition.** `held_eval.LOOP = ('budget_exhaustion', 'repetition')`, loop_rate = those outcomes / episodes ran. Every
looping episode in both runs is `budget_exhaustion`: the whole-case model-request budget of 64 (`max_model_requests`).
`repetition` never occurs. A wall-clock stop at 3600 s is `unresolved` (unscored) and is **not** counted as a loop.

**Paired view.** Budget-exhaustion flags on matched (task, sample): both 6, old only 13, new only 25, McNemar exact
p = 0.073: not significant. The old run had 9 wall-clock timeouts (new: 1), all at 36-59 model calls when cut; the old
run's episodes were slower (median 696 s vs 440 s per episode). Two of the 25 new-only loops are old timeouts at 45 and
55 calls. Counting "ran out" as budget or wall clock: old 28, new 33, discordant 19:24, p = 0.54. `held_eval compare`
(old -> new): 502 pairs (9 lost to timeouts), successes 223 -> 227, McNemar 38:42 p = 0.74, tasks 34 up / 32 down, delta
+0.8 pts, CI [-2.8, +4.4], loop_rate_delta +0.023. Calls per episode: mean 14.7 -> 15.7, median 10 -> 12; repeated-action
rate 0.0044 -> 0.0060.

**Harness delta between the pins** (17f1866c2..37c221bfe). The constant opening d17a253fc, typed return_result
f5aa37b68 and template-forced compaction d0bc72ae2 are in **both** pins, so they cannot explain a difference. What
changed for held collection: the same-question refusal text d0a192818, the dropped-promise fix b9152d612, removal of
leaf mode 06bd37a86 (a no-op here: `leafCalls` defaulted to `'tools'` and collection never set `'direct'`). The decision
readout ee9bb0b22 applies only to managed stock models.

**Same-question refusal (d0a192818).** It is hit in 13 (old) vs 14 (new) episodes. In the saved turns of failed
episodes, after the refusal the model returns directly 33% of the time with the new text vs 17% with the old.
Refusals per child invocation: 1.49 (max 4) vs 2.09 (max 3). The new text works as intended. More child invocations
hit it (37 vs 11): parents re-issue an ad hoc `nl` judgment whose child then delegates the same question again
(held row 13/1: `nl\`Decide whether item meets policy.\`(item)` per item, each child spending 3-9 calls). That pattern
is in both series.

**What the 64 calls go to (both series).** About 13-14 rejected actions per looping episode in both: `no-such-function`
from `read_code`/calls of the call's own name or invented helpers, and `transcript.search`/`transcript.entry` called as
tools (`bad-action`). In the new run there are also more `return: type-mismatch` rejections (44 in 8 episodes vs 9 in 1).
28 of the 44 are a record returned as a JS-object-literal **string** (`value: "{ facts: [...] }"` for
`{ facts: string[] }`), often resent unchanged. Typed return_result is in both pins, so this is episode mix, not a
code change. Some loops are not repetition at all: legitimate fan-out past 64 calls (row 163/0: 37 child invocations;
99/0: 24).

**Conclusion.** No harness change between the pins causes a behaviour loop. The loop-rate rise is the 9 old wall-clock
timeouts (episodes heading for 64 calls that the slower old run cut and did not count), plus noise (p = 0.073 on budget
flags alone, 0.54 with timeouts). Success is unchanged. No fix goes into the running pins. Candidates for the next
experiment boundary (first-principles harness fixes, not causes of this delta):
(1) when a call's declared return type is a record or array and `return_result.value` is a string holding a JSON or JS
object literal that checks against the type, accept the parsed value, making the idiom work. Otherwise name the fix in
the error ("pass the object itself, not its text"). First check whether JSON text is already parsed.
(2) Report budget and wall-clock stops together in `held_eval` (a "ran out" rate) so that throughput differences between
runs stop moving loop_rate.

**Done (2026-11-13, on main for the next experiment).** (1) return_result reads a string as JSON or a JS literal when the
declared result is a record/array/dict and checks the data (plans/MODEL_FACING_CHANGES.md). (2) `held_eval` reports
`ran_out_rate` (budget_exhaustion + repetition + wall-clock stops) in result.json and `compare` (rates, delta and a paired
McNemar `ran_out_paired`); `loop_rate` is unchanged. Older results get it computed from their samples in `compare`.
