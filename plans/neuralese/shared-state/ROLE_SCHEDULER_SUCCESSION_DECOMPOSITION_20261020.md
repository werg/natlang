# Automatic role exchange and semantic succession

`prepareSharedDialect(qualifiedSnapshots, currentOwners)` is the existing
natural-language training policy: keep both full recipes moving, preserve useful
qualified snapshots, prepare VAE with frozen backbones, then adopt genuinely
qualified released descendants before joint or policy updates. Readiness is
exact per-row communication exposure plus real task/runtime evidence, never an
aggregate visit counter or a simultaneous polling-window coincidence.

Extend existing units, not a parallel scheduler:

1. `native_deployment` binds coherent actual per-role plans, exact publishing
   control specs, semantic curriculum and existing provider resources. It emits
   the existing role relay and passive `native_readiness` configurations. It
   preserves every owned declaration, protected source and unfinished recipe.
2. `native_role_exchange` loads each actual reviewed controller's existing
   `load_controls` before source-host proof operations. Its SDK transport and
   artifact ferry remain unchanged; no credentials enter cloud workers.
3. Eligible proofs keep one durable exact qualified checkpoint per role while
   normal RAW/SFT status progresses. Snapshot preparation uses these historical
   qualified inputs only for frozen-backbone VAE work and grants no optimizer
   release or joint readiness.
4. The existing native readiness/semantic continuation path authenticates a
   real prepared VAE, requests actual descendant qualification and owner
   handoff, and resumes that VAE over released descendants with their exact
   optimizer/RNG/exposure. Joint/distillation/policy work starts only after the
   existing release checks. Actual tasks remain the quality gate.

Crisp code handles artifact bindings, authority equality, ownership, durable
requests, process supervision and exact CLI plumbing. There is no task prompt,
reward, model architecture, synthetic readiness or source-admission change.
Tests exercise the real relay/readiness protocols and serialized optimizer
continuation; fixture success does not qualify production CUDA capacity.
Deployment uses existing safe owner succession and the sole cloud operator.

The policy's post-preparation algorithm is:

1. Keep normal SGD/RAW cycles useful while each role earns actual communication
   exposure and its once-requested runtime/task checks. Withdraw current
   eligibility **before** submitting another optimizer operation. Preserve its
   immutable qualified snapshot separately.
2. Prepare VAE over those two frozen snapshots in its own output subtree. Keep
   the selected manifest fixed for that preparation; subsequent owner updates
   cannot replace its inputs. A frozen completion never grants joint readiness.
3. Authenticate its actual completion and the declared full joint/task/policy
   curriculum. Ask the existing relay to probe both actual owners/providers and
   their per-row candidates. Only the complete pair arms a handoff request.
4. At each owner's next normal boundary, run one actual qualification for that
   request generation. Keep earlier attempts in exact cursor history so moving
   back to ordinary work never repeats an old request automatically.
5. Hold a qualified descendant only under the explicit renewable provider lease
   and its own matching passed request. Peer failure cancels the lease; expiry
   also resumes useful work if the relay dies. The lease is an ownership
   handshake, not a token/update/time training cap or a quality certificate.
   Its duration is an explicit deployment value, chosen above actual relay
   roundtrip time, not an inferred scientific qualification threshold.
6. Once both current owners genuinely release, ferry their exact full assets
   through the existing role service. `snapshot_adoption` independently checks
   current release pointers, ancestor bindings and real task/runtime proofs.
   Resume the prepared checkpoint with `--refresh-participants` into a distinct
   joint output. Preserve descendants' optimizer/RNG/exposure; never merge or
   roll back their earned SGD into the older snapshots.
7. Existing joint/control/distillation phases and the existing full-episode
   semantic policy route run next. The bound native RL bootstrap uses the same
   admitted TRAIN tasks and both existing provider resources. Ordinary successful
   episodes remain eligible without a communication edge. Adapted episodes
   route to the shared semantic learner before standalone raw-stage handling.

Deployment entry point:
`python -m natlang_neuralese.train.native_deployment role-scheduler --spec <bound-inputs> --out <new-output>`.
The `natlang.native-role-scheduler-inputs/1` spec names `plans`, `controls`,
`curriculum`, `provider`, `raw_states`, `runtime`, `python`, `rl_bootstrap` and
`handoff_lease_seconds`. Bindings authenticate actual files. Both role contracts
must already agree on actual peer mechanism maps; no old R14 peer is relabeled
R4. The emitted plan copies require normal reviewed owner succession. The
emitted relay remains source-host-only SDK plumbing; cloud workers receive no
account credential. The actual running R4 package/owners are unchanged.

No new prompt, task oracle, error text, token renderer, training source or
intrinsic parser/index policy is introduced. Protected evaluation remains
read-only. Protocol fixtures test metadata and ownership, not production CUDA
capacity; actual tiny-port VAE/optimizer/resume tests cover state adoption.

Validation: ledger `native-role-scheduler-final-v9-20261020` ran 111 checks
successfully (one existing skip), including real two-port frozen VAE and
serialized descendant optimizer/RNG/exposure adoption. After adding joint asset
preflight, `native-role-scheduler-closure-v10-20261020` passed 82 focused protocol
checks (one existing skip). `native-role-scheduler-quick-20261020` passed all22
ratchets and TypeScript checking. No full-model or production CUDA qualification
is claimed. Root owns the integrated full suite.

Remaining operational cost: the first qualified descendant may pause while the
other existing owner finishes its real boundary/task/runtime check. The lease
prevents a lost relay/provider from leaving a permanent hold; it does not make
unequal-duration checks free. Existing task/runtime cancellation and supervision
remain responsible for failed work. Additional useful sealed-policy collection
or frozen adaptation during this handoff is a throughput opportunity, not an
implemented zero-idle claim. There is no implicit branch merge or earned-SGD
rollback to hide this cost.

Renewal correction: the VAE request is immutable, but each rendezvous has a
separate authenticated attempt containing both actual provider offers, current
checkpoint bindings, repair generations and the superseded attempt reference.
A live attempt renews; after expiry, actual SGD/owner/repair progress permits a
new attempt. Its SHA determines the fresh qualification generation. An unchanged
**current** eligible proof may be explicitly carried; a historical snapshot or
an advanced checkpoint cannot use that carry. Stale attempt rollback and
same-ordinal equivocation are rejected.

A failed task/runtime check is actionable repair evidence, not model rejection.
Useful SGD continues, but merely adding another SGD quantum does not rerun the
same failed two-hour check. Changing the existing explicit
`foundation_qualification_generation` after investigation/repair permits a new
attempt. Successful attempts interrupted by expired provider handshakes renew
automatically after real progress. Both source-host offers check their own
actual config/recipe/task/source file closure without decoding a checkpoint;
the consumer additionally uses the normal semantic dependency preflight.

Joint task declarations are explicit for each participant under
`models[model_id].task_eval`; no global Mellum baseline substitutes for LF.
LF's owner-authorized historical zero-success floor and its provenance are
honest policy, not a matched QAD measurement (DECISIONS.md, 2026-10-13). Mellum's
separately bound actual reference is retained. No new base evaluation is run.

## Resource ownership before frozen preparation

The scheduling policy is: stage both genuinely qualified snapshots and their
semantic closure first; hand the consumer's RAW owner directly into useful VAE
work while its peer keeps training. A snapshot is not permission to allocate a
second consumer model. Exact plumbing authenticates the preparation request,
requires the consumer's genuine dead-owner release before any semantic child
starts, and binds the source request to the staged snapshots/curriculum. The
existing RAW release validator and semantic child supervision remain authoritative.
On failed/cancelled preparation the consumer's preserved RAW cursor is reopened
through the same RAW coordinator, without claiming a shared-stage release or
resetting optimizer, RNG or exposure. A failed preparation needs explicit repair
before another preparation allocation; useful RAW work continues meanwhile.

Successful preparation consumes its exact allocation request through the existing
validated post-VAE handoff publication. The consumed marker binds the actual VAE
completion and checked source checkpoint identities; it cannot authorize backbone
updates and prevents the relay lending the same allocation again. Normal
operational cancellation is distinct from failed preparation: the next ownership
attempt binds its immutable predecessor/cancellation and changes the foundation
request generation after intervening RAW updates, while resuming the same saved
VAE checkpoint/exposure. Genuine failed preparation still needs declared repair.
