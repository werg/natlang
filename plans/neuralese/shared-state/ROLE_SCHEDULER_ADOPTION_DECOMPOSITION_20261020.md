# Normal role adoption before scheduler activation

Policy: continue both complete production recipes, retaining their actual state.
Prepare frozen semantic work as soon as both students have genuinely qualified
communication snapshots. Use the existing consumer RAW release to lend its
allocation; keep the peer training. Later joint and policy updates require the
existing qualified current-descendant handoff. No historical snapshot grants
current-weight qualification.

1. The supervisor selects the reviewed normal later-runtime role inputs, the
   complete semantic curriculum, each participant's task policy, and existing
   provider resources. This remains natural-language operational policy.
2. A crisp metadata preparer authenticates those inputs and calls the existing
   `native_deployment.prepare_role_scheduler`. It emits the exact inputs to the
   existing `prepare_native_actor_role` utility, replacing only its bootstrap
   with the scheduler-enabled source plan. It does not fabricate a controller
   or owner receipt, decode a checkpoint, or apply a handoff.
3. Normal role/runtime succession consumes these inputs. Its existing ownership,
   recipe, optimizer, RNG, exposure and numerical checks remain authoritative.
4. A crisp reconciliation pass authenticates both actual published controller
   specs and their actual RAW configuration plan bindings. Only then does it
   emit the existing relay and passive readiness launch commands. It preserves
   actual adopted plan paths instead of treating copies as current authority.
5. The existing relay/controller perform readiness, resource handoff, frozen VAE,
   adjustable refresh, joint/control/distillation and whole-graph RL. This
   preparer adds no scheduler, trainer, provider queue or readiness verifier.

Preparation is repeatable through a new output namespace. Reconciliation waits
when a normal successor has not been published; conflicting published identity
fails explicitly. An output receipt is never an activation/readiness receipt.
The immutable source composition is independently reviewed before deployment.
No executing model sees new text.

## Operational interface

`prepare_native_scheduler_adoption.py prepare --spec INPUTS --out NEW_DIRECTORY`
uses schema `natlang.native-scheduler-adoption/1` with exactly:

- `composition`: checked construction.json binding of the physically installed
  reviewed complete runtime, not an overlay.
- `roles`: `lfm` and `mellum`, each containing `inputs` (the normal role utility's
  checked input JSON) and the actual absolute `raw_state` path. Their source
  bootstraps retain real own recipes, commands, unfinished work and prerequisites.
- `scheduler`: existing `native_deployment.prepare_role_scheduler` arguments:
  checked `curriculum`, `provider`, `rl_bootstrap`; physical `runtime`; `python`;
  explicit `handoff_lease_seconds`; optional checked `snapshot_parent`.

The normal R6 input for each role must already select that reviewed actor runtime.
The helper joins each actual own declaration, replaces stale peer copies with
those declarations, and uses both composed six-mechanism maps. It does not invent
an actor command or rewrite a custom command. Each generated normal-input JSON
retains the authenticated original inputs and source plan as frozen dependencies.
The receipt contains exact argv for the existing normal role utility. Normal
binder/runtime succession remains a separate, supervised operation.

After the real owner handoffs, run `reconcile --prepared PREPARED --published
PUBLISHED --out NEW_DIRECTORY`. PUBLISHED maps each role to checked `spec`,
`entered` and fresh `raw_config` bindings from the existing publication mechanism.
Missing files yield a waiting result; conflicting published facts fail. An actual
normal handoff may carry a newer additive recipe. Reconciliation uses its actual
owned recipe/seed/held/cases in the RL bootstrap, while retaining the selected RL
policy and exact native participant identity. This grants no exposure.

The resulting passive readiness controller runs on the existing Mellum consumer;
its command, workdir and explicit runtime environment are in ready-to-launch.json.
The SDK relay runs on DGX instead. `stage-host-relay --provider PROVIDER --ready
READY_BINDING_JSON --source-host CONSUMER_ID --composition LOCAL_REVIEWED_RUNTIME
--python SDK_PYTHON --out NEW_DIRECTORY` reads only the small ready/relay metadata
through the existing SDKIO bound-read helper. It requires the same resource,
provider and code identities, retains the original bytes, and changes only the
relay's host-local state directory. Its receipt contains the host launch argv and
environment. No cloud credentials enter the consumer. The normal source-host
service environment supplies SDK credentials, as for the existing provider worker.
Both launch receipts remain `activated=false` until the supervisor actually starts
and monitors the existing processes.

Run an externally staged copy with `NATLANG_REPO` and `PYTHONPATH` selecting its
reviewed complete runtime. Its compose/verify imports come from that runtime,
not from the external helper's parent directory. No source tree is hot-patched.
