Owner decision 2026-10-28: the LFM line switches from LFM2.5-350M (QAD) to `LiquidAI/LFM3-1.7B` (instruction-tuned,
revision `40ebe0aa6662c9d40389c2f5d565b6a2c6aebacd`); production training was stopped for the switch. Base task

lineage history until cutover and retention review.

## Architecture facts (checked against the pinned remote code)

conv (L_cache 7, no bias) / full_attention (partial "zero-tail" RoPE 0.5, theta 1e6) / sliding_attention (window
256, RoPE theta 1e4) layers; QK RMSNorm (`q_norm`/`k_norm`), `o_proj`, per-head sigmoid output gate
`self_attn.gate_proj` (2048->16) computed from the normed attention input; sandwich norm (`post_operator_norm`,
`post_ffn_norm`); LFM2 names elsewhere (`operator_norm`, `ffn_norm`, `feed_forward.w1/w2/w3`, `conv.in_proj/out_proj`,
`embedding_norm`); hidden 2048, 24 layers, 16 heads / 4 KV, head_dim 128, vocab 128000 tied (rows 125033+ unused);
BF16 weights. Tokenizer: ChatML with `<|startoftext|>` BOS, reasoning on by default (`<think>` opens the generation
prompt), XML tool calls `<tool_call><function=NAME><parameter=K>VALUE</parameter></function></tool_call>` with
unquoted string values; `<|tool_call_start|>` remains in the vocabulary but is unused. transformers 5.18 has no
`lfm3`: the modeling code is vendored at the pinned revision with its sha256 and is the exact parity reference.

**Format detection.** `serve/chat.TOOL_CALL_FORMATS` declares each backbone's call serialization by `config.model_type`
(`lfm2` pythonic, `mellum`/`qwen3` json, `lfm3`/`qwen3_5` xml). `data/render.SpecialIds`, the serving engine
(`Engine.tool_call_format`), guidance, `text_corpus.tokenizer_call_format` and the twin tooling read it; nothing
inspects the vocabulary (LFM3 still holds `<|tool_call_start|>`). An undeclared backbone is an error in `render.py`.

**XML value boundary (write sites).** LFM3 writes `<tool_call>\n<function=NAME>\n<parameter=KEY>\nVALUE\n</parameter>\n
…</function>\n</tool_call>`: a string value verbatim, any other value its canonical JSON (`tojson`: `", "`/`": "`
separators, keys unsorted). The template has no escape, so the format's one exact rule (llama.cpp's Qwen3-Coder/LFM3
parser) is the boundary: a value ends at the first `"\n</parameter>\n"` after its opening line.
- Representable value: `(v + "\n</parameter>\n").find("\n</parameter>\n") == len(v)` (`xml_value_representable`).
  `</parameter>` elsewhere in code is fine; `<tool_call>`, `<function=…>` and the other added tags inside a value are
  content (they tokenize as the same added tokens the base model saw; parsing is structural, so they cannot open a
  call inside a value).
- Unrepresentable calls fail loudly (`RequestError('tool-call-unrepresentable')`): prompts check structure (names
  without `>`/newline, delimiter-free values); training targets also check that each value keeps its type, since the
  model learns the text and the parser assigns the type.
- Typing: a string-only schema parameter is verbatim; other declared types are JSON first; an undeclared parameter is
  JSON only when its text is exactly the template's canonical rendering of a non-string (`{"a":1}` stays a string,
  `{"a": 1}` is an object). A string whose text equals such a rendering (`42`, `true`) is inherently ambiguous without
  a schema: training targets refuse it, serving reads it as JSON like llama.cpp.
- Write-site cut (`call_reply`/`write_reply`/`write_value_text`): the prefix ends with `<parameter=KEY>\n`, the suffix
  starts with `\n</parameter>\n`. String and `unknown` sites share that boundary (no quotes to strip); the producer's
  block sits between them and parses back as a `native_state` part (a whole-value placeholder is kept even under a
  non-string schema). A site nested inside a JSON-valued parameter is a quoted JSON string, as in the other formats.
  A declared format that disagrees with what the template renders is an error.
- Producer targets keep the complete original response: `native_gold_packet` places the role markers around the
  template's own rendering of the value (a string verbatim, an `unknown` value its canonical JSON) between the
  parameter's lines; removing the markers gives byte-for-byte the plain rendering of the original call. Inline spans
  in `eval` code are verbatim (`rendered_body == body`).
- Guidance under XML reads `<function=NAME>` lines and the verbatim `<parameter=code>` value; `require_call` cannot be a
  forced prefix (the reply opens with reasoning), so the text after `</think>` must open `<tool_call>` (`no-call`).

**History reasoning.** LFM3 declares `keep` (template `preserve_thinking=true`). The template default rewrites earlier

history spans. Natlang invocations render identically either way. Recorded as model-facing debt.

## CPU flash-attention precision gap (diagnosed and fixed 2026-10-28, fork 85a2e7167)

Symptom (part C): on CPU (`-ngl 0`) LFM3 key captures differed from the HF fp32 reference by up to 0.21 vs 0.025 on GPU,
starting at the first attention layer's output. Dragnet (`/home/werg/data/lfm3-port-c/cpugap{1,2,3}/report.json`),
max |k - ref| at layers 4/6/8:
- CPU flash attention on (default auto), F32 or F16 cache: 0.039/0.150/0.213 (identical for both caches);
- CPU flash attention off, F32 cache: 0.004/0.029/0.034; F16 cache: 0.005/0.033/0.036 (F16 storage is harmless);
- CPU flash attention on with F32 K/V (diagnostic: llama-graph's F16 cast skipped): 0.004/0.030/0.036;
- GPU: 0.007/0.016/0.016; thread count irrelevant.
Cause: `src/llama-graph.cpp` casts F32 K/V to F16 before `ggml_flash_attn_ext` (meant for cache-less models, but it
also fires with an F32 cache), and the CPU per-row kernel `ggml_compute_forward_flash_attn_ext_f16_one_chunk`
(used for decode and for ubatches under the 64-row tile, e.g. the 24-token produced span) accumulates softmax(KQ)*V
in an FP16 buffer when V is F16. The tiled CPU kernel and CUDA accumulate in FP32.
Fix: the per-row kernel accumulates in FP32 for F16 V (`GGML_CPU_FA_F16_ACC=1` restores upstream). After: 0.005/
0.029/0.028 (layer 22: 0.026 vs 0.122 before). This affects every CPU decode, including the browser/wllama path,
which needs a rebuild from the fork. Open: CPU decode throughput impact not yet measured; candidate upstream PR.
