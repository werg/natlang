# Product opportunity portfolio manager — semantic decomposition

`planPortfolio.nl` works from customer evidence and an immutable strategy baseline. It branches first on sponsor priority events: a supported mid-cycle change creates a separate scenario fork, while the approved baseline stays intact. For each planning frame, `separateUnderlyingNeed.nl` recovers the desired outcome and workflow without mistaking a feature request for the need. `proposeDistinctMechanisms.nl` then creates materially different service, process and product approaches, including a low-change baseline. For each mechanism, `decomposeOpportunityWork.nl` separates bounded enabling packages and source-backed cost ranges; `identifySharedPortfolioWork.nl` groups shared dependencies and avoids duplicate benefit claims. `selectDecisionTestForMechanism.nl` asks whether a least-cost evidence-supported test can change a decision and makes its positive, negative and inconclusive consequences explicit.

The root returns an `PortfolioStrategyAssessment`, not accepted investment records. The supplied `FeasiblePortfolioSet[]` receipts remain unaccepted until their estimate-set and exact constraint digest can be matched to the derived packages. A positive receipt binding is possible when the host supplies typed `derivedEstimates` plus a `constraintArtifacts` record whose frame, strategy, horizon, budget, capacity, solver version, estimate IDs, shared-work IDs, and digest exactly match the receipt. If any field is absent or mismatched, the receipt review states the specific defect; the program does not calculate totals or invoke a solver. Unknown cost and capacity stay unresolved. The public operation accepts a `PortfolioDecisionCheckpoint` and retains assessment editions and priority forks against their exact approved baseline. Changed estimates or priorities supersede only affected options; identical receipt replay is a no-op. The checkpoint retains unresolved investment approvals; feasibility does not authorize funding.

The optional mid-cycle sponsor fork is explicitly null unless a supported event creates one. Baseline assessment, receipt review and checkpoint reconciliation therefore receive a stable value on both the ordinary and forked paths.

The five original domain obligations are owned directly by the mechanism-specific source modules: underlying need reconstruction, distinct intervention generation, dependency decomposition, solver-receipt qualification at the portfolio boundary, and decision-changing experiment selection. The original first-gate fixture is retained unchanged, including its supported, contradicted and incomplete cases. Operational scenarios stay review proposals: mid-cycle priority changes fork rather than overwrite; a shared dependency is charged once; a missing estimate prevents firm feasibility; one quote is not counted as several independent customers; and an inconclusive test leaves the decision unresolved.

Dependency estimation now reasons through child results: each work package is attributed to its enabling mechanism and source estimate, and shared work is linked to all consuming mechanisms before the aggregate is passed to portfolio comparison. The root uses the resulting cost attribution and shared-benefit checks when reviewing exact solver receipts, so a correct receipt over a differently grouped estimate set cannot qualify.
