## Proposed shape (what the "natlang unit / caller" column refers to)

pi-durable runs a turn as three durable task kinds: `pi.generation`, `pi.tool` and `pi.compaction`. The scheduler
(another group) calls a task's phase handler with its checkpoint. Each handler ends by committing the task's next
state: `running` with a new checkpoint, `waiting` on child tasks with policy `allSettled`, or `terminal` with an
outcome. The port keeps that split:

- **Natural-language functions, one entry per task kind, with phases as branches.**
  - `generation` (branches prepare / request / retry / poll / tools / abort). Its companion folder `generation/` holds
    `prepare`, `request`, `classify`, `answer`, `start-tool-round`, `finish-tool-round` and `abort`.
  - `tool` (branches call / execute / abort). Its folder `tool/` holds `call` and `run`.
  - `compaction` (branches select / summarize / retry / abort). Its folder `compaction/` holds `select` and
    `summarize`.

  The companion-folder rule forces one entry per kind. `classify` runs after both `request` and `poll`, and `run` runs
  after both `call` and recovery (`execute`), so whatever calls them must be the folder's parent. Every phase function
  commits, or returns for its caller to commit, exactly one next-state record.
- **Services, implemented in the host:**
  - `durable` is the invocation's task runtime:
    - `commit(change)` is an atomic commit on the Session line. `change` receives a `tx` with `appendEntry`,
      `doc(token)`, `createTask`, `scanEntries` and `settleSubmission`, and returns the next state or nothing.
    - `context(conversationId, {at?})` returns the committed ContextView. `agent()` returns the phase's agent
      resolution, which stays fixed for the phase. `settings` is resolved anew on every read.
    - Also `outcomes(taskIds)`, `entry(token, id)`, `snapshot(doc)`, `env()`, `sleep(until)`, `now()`,
      `report(error)`, `memo` and `signal` (the abort mark).
    - `hooks.each(name, invoke)` dispatches hooks (scheduler.ts:1131-1143). It calls each handler named `name` among
      the selected extensions' hooks for this task kind, in extension order. An ordinary throw is reported and
      dispatch continues; once the invocation is aborted, the throw propagates.
  - `models` is pi-ai: `getModel`, `streamSimple`, `completeSimple`, `fetchDeferred` and `cancelDeferred`.
  - `toolRuntime` runs one tool implementation with its execution api.
  - `registry` is the process-local extension registry.
- **Crisp helpers.** One shared callable folder, here called `harness-kit`. It holds every unit marked crisp below and
  the pure pi-ai helpers they import:
  - `isContextOverflow` matches provider error-text patterns.
  - `isRetryableAssistantError` accepts transient patterns (overloaded, 429/5xx, rate limit, network, timeouts, stream
    ended early, and similar) but not quota or billing errors.
  - `retryDelayMs(policy, attempt)` = `min(baseDelayMs * 2^(attempt-1), maxAgentDelayMs ?? 60000)`.
  - `estimateMessageTokens` = `ceil(chars / 3.5)`. An image counts as 4800 chars, a tool call as its name plus
    JSON(args), and a system message as its text plus the JSON of its tool lists.
  - `calculateContextTokens(usage)` = `totalTokens`, or `input + output + cacheRead + cacheWrite` when that is 0.
  - `getCurrentTools`, `declarationsEqual`, `toToolDeclaration` and `validateToolArguments`.

Shorthand in the tables:

- "fail run (reason)" means the crisp `failRun` helper.
- `ctx@cutoff` means `durable.context(conversation, {at: cutoff})`.
- "the run" means `pi.live.run`: the task that settles the run's input submissions, and those inputs.

Notes. generation.ts depends on:

- compaction: `createCompaction`, `estimateContext`, `selectCut`;
- prompt: `replaySections`, `renderSections`, `planSystemEntries`;
- tool: `appendToolResult`, `harnessError`, `ToolTask`;
- agent: `addTools`;
- inbox: `prepareBoundary` and `applyBoundary` (submissions group);
- live, provider and usage.

live.ts imports `convertPartial` back. That cycle is harmless once both are crisp. State lives in three places: the task checkpoint, `pi.live` (`run`, `generation`, `tools`) and the transcript entries.

A run is a chain of durable tasks: generation, then a tool round, then the next generation, joined by `handOver`. Because it is not an eval loop, natlang's `iterateOn` does not apply. **pi has no cap on tool rounds.** The only bounds are `maxRetries` per chain of attempts and one blocking compaction per generation (`compacted`). Whether the port should add a round cap, checked in `finish-tool-round`, is an owner decision. The throttled partials in `live.generation.message` are presentation state, a natural fit for an `EventLoop` reducer (event "partial", commit before publish).

Notes.

**When compaction triggers.**

- Threshold, at generation `prepare`. Blocking compaction triggers when the estimate exceeds `contextWindow - reserveTokens`; background compaction when it exceeds `contextWindow - reserveTokens - backgroundTokens`. The defaults are reserve 16384, keepRecent 20000 and background 32768. Neither triggers without a cut.
- Overflow, at classify, once per generation.
- Manually, via `Conversation.compact()` (other group).

**What it keeps.** Everything from the first candidate at or after the point where the newest entries reach `keepRecentTokens`. The summary becomes the new head marker's user message. The next preparation finds a head marker without a later `pi.system` entry and writes a full system baseline (prompt.ts).

Compactions do not coordinate with each other; §6 decides between their summaries.

The scheduler cleanup (live.ts) removes the status of a faulted or orphaned compaction.

**Owner decision: who writes the summary.** pi sends the verbatim prompts to the conversation's own model with no tools. The port can keep that as a service call made by `compaction/summarize` (recommended: the summary quality matches the agent model). The alternative is a natlang fn `summarize-conversation(serialized, instructions) -> string` whose body is the prompt, run by the fast executor model. That is cheaper but weaker, and its usage would not land in `pi.usage`.

## Cross-cutting: hook points

All hooks are dispatched by `durable.hooks.each` in extension order. An ordinary throw is reported and dispatch continues, except where noted. Hooks may rerun after a crash, so durable decisions should use task memos, which share one namespace with the task's own memos.

| hook | asked by | arguments | composition | ordinary throw | effect |
|---|---|---|---|---|---|
| `beforeRequest` | `generation/request`, every attempt including recovery | `{messages}`: the committed context through cutoff | replacement chain | report, continue | replaces the messages sent in this request only; the offered-tools check still uses the committed context |
| `afterResponse` | `generation/classify` | the terminal message (not a still-deferred one) | all observers | report, continue | none on the turn |
| `onYield` | `generation/answer` | the final answer | first `{continue}` wins | report, continue | appends a user message and continues the run, but only when the final boundary selected no user item and no reset; otherwise dropped |
| `afterTools` | `generation/finish-tool-round` | `(assistant entry, result entry ids in call order)` | all observers | report, continue | none on the turn |
| `beforeTool` | `tool/call` | the call, with the current args | argument replacement chain; first `block` wins | becomes a block with the error text | `blocked` error result, or new args (validated again) |
| `afterTool` | `tool/run` | `(call, assembled result)` | result replacement chain | report, continue | replaces the result before truncation and the entry are written |
| `beforeCompact` | `compaction/select` | `{reason, entries, messages, firstKept, instructions?}` | first decision wins | report, continue | `{decline}` completes with no summary; `{summary}` is placed instead of summarizing |

## Owner decisions collected

1. **Round cap.** pi-durable has no limit on tool rounds per run. Add a cap, iterateOn-style, in `finish-tool-round`, or keep it unbounded?
2. **Summary writer.** Should `compaction/summarize` keep pi's provider call to the conversation's model with the verbatim prompts (recommended), or become a natlang fn run by the executor model?
3. **Crisp versus natural language for derivations.** Context derivation (context.ts), prompt and tool diffing (prompt.ts), agent resolution and cut selection are marked crisp because they are exact pure reducers over long data, with their rules spelled out above. The criteria lists "context and system prompt assembly" as natural-language behaviour. Confirm crisp, with the natural-language contract stated in `generation/prepare` and `generation/request`.
4. **Extensions in natlang.** What is an extension (tool fns, section fns or text, hook fns)? How are higher-order wrappers (`wrapTool`, `wrapSection`) expressed, or are they dropped? Does in-process reload (§7.5) carry over?
5. **Presentation state in `pi.live`.** Keep the throttled partials and tool progress, possibly via an `EventLoop` reducer, or only the run-control half?
6. **Entry-per-task layout.** One natlang entry fn per task kind (`generation`, `tool`, `compaction`) with phase branches, because of the companion-folder rule (`classify` after request and poll; `run` after call and recovery). Confirm that the scheduler service calls these entries with the checkpoint, and that the shared crisp helpers live in one shared `harness-kit` folder.
7. **Tool replay.** Should natlang tools declare `replay: safe/unsafe` and keep the intent checkpoint? Recommended, since recovery depends on it.
